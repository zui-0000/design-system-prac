# UX のルール

記録日: 2026-10-15 / 元にしたサイト: [UIデザイン心理学辞典](https://ui-psychology-dictionary.pages.dev/)

デザインシステムで守る UX のルールを、UIデザイン心理学辞典に載っている 30 の法則をもとに作った。この文書には、ルールをどこに置いたかと、その理由をまとめる。ルールの本文は `.claude/rules/ux.md` にある。

## まとめ

- Claude に読ませるルールは、SKILL ではなく `.claude/rules/ux.md` に置いた。`paths` で `src/components/**` と `src/styles/**` に絞ってある
- 30 の法則を、次の 3 つに 10 個ずつ分けた
  - A: トークンやコンポーネントの作りに入れるもの
  - B: 画面を組み立てるときの判断として Claude に渡すもの
  - C: デザインシステムの範囲の外のもの
- C からは、ダークパターンの禁止だけをルールに入れた
- サイトの文章は写さず、自分たちの言葉で書いた。このリポジトリは公開していて、サイトにはライセンスの表記がないため

## ルールをどこに置くか

### ルールは「お願い」でしかない

CLAUDE.md・SKILL・`.claude/rules/` は、どれも Claude に読ませる文章でしかない。Claude Code の公式ドキュメントにも「Claude treats them as context, not enforced configuration」とある。それに、相棒が自分でコードを書くときには何の効果もない。

そこで、ルールを守らせる方法を、強い順に 4 つに分けて考えた。

| 方法                                      | 例                                                          | 守られ方                                                       |
| ----------------------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------- |
| 1. トークンやコンポーネントの作りに入れる | 押せる部品の高さを 44px 以上にする                          | 部品を使えば自動で守られる。人が書いても Claude が書いても同じ |
| 2. 機械でチェックする                     | Storybook の a11y チェック、Oxlint の `jsx-a11y` プラグイン | 違反すると `vp test` や `vp check` が失敗する                  |
| 3. Claude に読ませる                      | `.claude/rules/`、SKILL                                     | Claude が読めば守る                                            |
| 4. 理由を書く                             | `docs/`                                                     | 人が読んで理解する                                             |

1 と 2 を増やすほど、3 に書くことが減って確実になる。TS で言えば、「`any` を使わない」と README に書くより、`noImplicitAny` と lint で止めるほうが確実なのと同じ。

### SKILL ではなく `.claude/rules/` にした理由

docs/01 では「docs に本体、SKILL から参照」と決めていた。比べ直して、`.claude/rules/` に変えた。

|                  | SKILL                                                                         | `.claude/rules/*.md`（`paths` 付き）                           | CLAUDE.md                |
| ---------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------ |
| 読み込まれるとき | 説明文は毎回。本文は、Claude が関係あると判断したときか、`/名前` で呼んだとき | `paths` に合うファイルを、Claude が Read・Write・Edit したとき | 毎回                     |
| 確実さ           | Claude の判断しだい                                                           | 合うファイルに触れば必ず                                       | 必ず                     |
| 向いているもの   | 手順のある作業、長い参考資料                                                  | いつも守るルール                                               | 全体に関係する短いルール |

UX のルールは、UI を書くときにいつも守るものなので、Claude の判断を待つ SKILL は合わない。コンポーネントを作る手順がまとまってきたら、手順のほうを SKILL にすることを考える。

### `paths` の書き方

`paths` は、ルールのファイルの先頭（フロントマター）に書く設定。ルールのファイルの場所ではなく、「Claude がどのファイルを触ったときに、このルールを読み込むか」を glob で指定する。TS で言えば、tsconfig の場所と `include` に書いた対象のファイルが別物なのと同じ。

```markdown
---
paths:
  - "src/components/**"
  - "src/styles/**"
---
```

`paths` を書かなければ、セッションの開始時に毎回読み込まれる。

UX のルールが関係するのは、コンポーネントとスタイルを触るときなので、この 2 つに絞った。`vite.config.ts` や `docs/` だけを触る作業では読み込まれない。

### 新しいファイルを作るときは、最初の書き込みの後に届く

スクラッチのプロジェクトで、`paths: ["src/**/*.tsx"]` のルール（「1 行目を `// RULE-LOADED` にする」）を置いて、別の Claude（`claude -p`、Claude Code 2.1.299）に「`src/Hello.tsx` を新しく作って」と頼んだ。

1. Write で `Hello.tsx` を作った。このときはまだルールを知らないので、1 行目のコメントがない
2. Write の後に、ルールが読み込まれた
3. ルールを読んだ Claude が、Edit でコメントを足した

今回は Claude が自分で直したが、新しいファイルは「書いてから直す」流れになる。既にあるファイルを直すときは問題ない。Edit の前に必ず Read するので、その時点でルールが届く。

`src/styles/**` を `paths` に入れておくと、この問題が少し和らぐ。新しいコンポーネントを書く前に、Claude はたいていトークン（`src/styles/` の中）を読むので、そこでルールが届く。ただし、必ず読むとは限らない。

### 気をつけること

- **フォルダ構成を変えたら、`paths` も直す。** `paths` が実際のフォルダと合わなくなっても、エラーは出ない。ルールが黙って読まれなくなるだけ。モノレポにして `packages/ui/` に移すときなどに注意する
- **ページやレイアウトを置く場所を決めたら、`paths` に足すか考える。** UX のルールは、画面の組み立て（レイアウト、レスポンシブ）にも関係する
- **読み込まれたかを確かめる方法**: セッションの開始時に読み込まれるファイルは `/context` で分かる。`paths` 付きのルールが読み込まれたタイミングは、`InstructionsLoaded` フックでログを取ると分かる。上の実験では、ログに `load_reason: "path_glob_match"` と、きっかけになったファイルが記録された

## 元にしたサイト

[UIデザイン心理学辞典](https://ui-psychology-dictionary.pages.dev/) は、UI に効く心理学の法則を 30 個、6 つのカテゴリに分けて載せている。どの法則にも、悪い例・良い例・効く理由・使いどころ・注意点がある。「ラベルと入力欄の間は 4px、次の項目までは 16px」のように、具体的な数字があるのがよい。

サイトには、定義の文章と UI の例は独自に作ったと書かれていて、ライセンスの表記はない。このリポジトリは GitHub で公開しているので、サイトの文章はそのまま写さず、自分たちの言葉で書いた。法則そのもの（フィッツの法則など）は広く知られた知見で、44px や 400ms のような数字も事実なので、そのまま使っている。

## 30 の法則の仕分け

### A. トークンやコンポーネントの作りに入れる（10 個）

| 法則                      | 内容                                                               | このデザインシステムでやること                                                  | 段階       |
| ------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------- | ---------- |
| 01 視覚的階層             | 大きさ・太さ・余白の差を、重要さの差として読む                     | 文字の大きさと太さのトークンを作る。強調は「主・副・補足」の 3 段まで           | 2（済）    |
| 03 近接の法則             | 近くにあるものは、同じまとまりに見える                             | 余白のトークンを作る。グループの中は狭く、グループの間は広く（例: 4px と 16px） | 1・2（済） |
| 07 フィッツの法則         | 遠くて小さい的ほど、押すのに時間がかかる                           | 押せる部品は縦横 44px 以上にする                                                | 2・3（済） |
| 02 フォン・レストルフ効果 | 1 つだけ違うものが記憶に残り、選ばれやすい                         | ボタンの種類（primary など）を用意する。目立たせるものは 1 つの領域に 1 つだけ  | 3（済）    |
| 10 段階的開示             | まず多くの人に必要なものだけを見せ、詳しいものは求められたら見せる | 開閉できる部品（Accordion など）を作る                                          | 3          |
| 11 ドハティの閾値         | 反応が 0.4 秒を超えると、集中が切れる                              | Skeleton を作る。1 秒未満で終わる処理には出さない                               | 3          |
| 12 意図的な壁             | 取り消せない操作には、あえて手間を足す                             | 確認ダイアログを作る。影響が大きいものは名前を入力させる                        | 3          |
| 13 ヤコブの法則           | ユーザーは、ほかのサイトと同じ動きを期待する                       | 部品の動きは Base UI（WAI-ARIA の標準に沿った動き）に合わせる                   | 3          |
| 16 ツァイガルニク効果     | 終わっていないことは、気になり続ける                               | 進み具合の表示（Progress、Stepper）を作る。残りの項目を見せる                   | 3          |
| 25 目標勾配効果           | ゴールが近づくほど、頑張れる                                       | 同上。完了したら次のゴールを見せる                                              | 3          |

段階は docs/01 の 5 段階のこと。作ったら、この表に「済」と書いていく。

- 2026-10-18: 段階 2 の分を済にした（[docs/12](12-デザイントークン.md)）
  - 01 視覚的階層: 文字サイズと太さのトークン（`src/styles/tokens/font.css`）
  - 03 近接の法則: 余白のトークン（`src/styles/tokens/spacing.css`）。Card の中は 12px、カードの間は 24px
  - 07 フィッツの法則: 押せる部品の最小の大きさ `--size-touch-target`（44px）。段階 3 で Button などに使ったら、残りの「3」も済にする
- 2026-10-18: Button を作った（[docs/13](13-Base%20UI%20と%20Button.md)）
  - 02 フォン・レストルフ効果: ボタンの種類を primary と secondary にした。何も指定しなければ secondary で、目立たせるボタンだけ `variant="primary"` と書く
  - 07 フィッツの法則: Button の押せる範囲を 44px 以上にした（`--size-touch-target`）
  - 13 ヤコブの法則: Button から Base UI を使い始めた。ほかの部品を作るたびに続けるので、まだ済にしない

### B. 画面を組み立てるときの判断として、Claude に渡す（10 個）

| 法則                      | 内容                                     | ルール                                                 |
| ------------------------- | ---------------------------------------- | ------------------------------------------------------ |
| 06 ヒックの法則           | 選択肢が多いほど、決めるのに時間がかかる | 一度に見せる選択肢を減らす。残りは「その他」にまとめる |
| 08 認知負荷               | 処理しきれない量を見せると、離脱する     | フォームは今必要な項目だけにする                       |
| 09 ミラーの法則           | 短期記憶に入るのは 4±1 のまとまり        | 長い値は 4 桁前後に区切る                              |
| 24 決断疲れ               | 決めることが多いほど、判断の質が落ちる   | おすすめを 3 つ程度、理由付きで先に見せる              |
| 14 系列位置効果           | 最初と最後が記憶に残る                   | 一番大事な項目は両端に置く                             |
| 04 バナー・ブラインドネス | 広告に見えるものは読み飛ばされる         | 大事なお知らせを広告のような見た目にしない             |
| 05 美的ユーザビリティ効果 | 整った見た目は、使いやすく感じる         | トークンと部品を使って、見た目をそろえる               |
| 20 デフォルト効果         | 人は初期値をそのまま受け入れる           | 初期値はユーザーのためになるものにする                 |
| 15 ピーク・エンドの法則   | 体験の評価は、一番の山場と終わりで決まる | 完了やエラーの画面を丁寧に作る                         |
| 17 労働の錯覚             | 作業が見えると、結果の価値が高く感じる   | 時間がかかる処理は、実際の手順を見せる                 |

ミラーの法則は「7±2」として知られている。これは 1956 年の Miller の論文の数字で、その後の研究（Cowan など）では 4 前後とされている。サイトも 4±1 を使っている。「メニューは 7 個まで」はこの法則の誤用で、項目の数はヒックの法則で考える。

### C. デザインシステムの範囲の外（10 個）

アンカー効果、おとり効果、損失回避、フレーミング効果、希少性、変動型報酬、サンクコスト効果、社会的証明、ハロー効果、授かり効果。

値段の見せ方や文言のように、プロダクトの企画で決めること。部品の作りとはあまり関係がないので、ルールには入れていない。ただし、どの法則の注意点にも「やりすぎるとユーザーをだますことになる」という話がある。それをダークパターンの禁止としてルールに入れた。

## ダークパターン

**ユーザーをだましたり焦らせたりして、本人が望んでいない行動をさせる UI** のこと。サービスの側が得をして、ユーザーの側が損をする。2010 年に UX デザイナーの Harry Brignull が名前を付けた。今は「deceptive patterns（欺くパターン）」とも呼ばれる。

### 心理学の法則は両刃の剣

上の 30 の法則は、ユーザーのために使えば良い UI になり、ユーザーをだますために使えばダークパターンになる。

| 手口                   | 例                                                                     | 悪用している法則             |
| ---------------------- | ---------------------------------------------------------------------- | ---------------------------- |
| 偽の希少性・偽の期限   | 在庫があるのに「残り 1 点」と出す。開き直すたびに戻るカウントダウン    | 希少性                       |
| こっそりオン           | メールの配信や有料のオプションに、最初からチェックが入っている         | デフォルト効果               |
| 入りやすく、出にくい   | 登録はボタン 1 つなのに、解約は電話でしかできない                      | 意図的な壁（向きが逆）       |
| 断ると罪悪感           | 断るボタンの文言が「いいえ、損してもかまいません」                     | 損失回避、フレーミング効果   |
| 広告を本文に見せかける | 広告を、記事やダウンロードボタンと同じ見た目にする                     | バナー・ブラインドネスの逆用 |
| 偽の元の価格           | 実際には売っていない「通常価格」を並べる                               | アンカー効果                 |
| 隠れた費用             | 最後の確認画面で、急に手数料が足される                                 | サンクコスト効果             |
| 紛らわしい質問         | 「配信を希望しない場合はチェックを外さないでください」のような二重否定 | 認知負荷                     |

同じ「手間を増やす」でも、削除の前の確認はユーザーをミスから守る壁で、解約のときだけ手順を増やすのはユーザーを逃がさない壁になる。**誰のための手間か**で正反対になる。

見分けるときは「**ユーザーがすべての事情を知っていても、同じ選択をするか**」と考える。答えが No なら、ダークパターン。

### ルールに書く理由

- **短い間は効くが、長い目で見ると損をする。** 登録や購入は一時的に増えるが、だまされたと気づいたユーザーは離れ、悪い評判も広まる
- **法律で禁止され始めている。**
  - EU のデジタルサービス法（DSA）は、ユーザーをだましたり操作したりする画面の作りを禁止している
  - 日本では、2022 年の特定商取引法の改正で、通販の最終確認画面に、価格や契約期間などをはっきり表示することが義務になった
  - 実際には売っていない「通常価格」との比較（二重価格）は、景品表示法の問題になる
- **Claude が「よくある手法」として書いてしまうことがある。** 「登録を増やしたい」と頼まれると、偽の期限やチェック済みの同意欄を出してしまうかもしれないので、禁止事項として書いておく

## 数字の根拠

| 数字                               | 根拠                                                                                                                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 押せる範囲 44px 以上               | WCAG 2.2 の基準では、最低限（AA、2.5.8）が 24×24px、より高い基準（AAA、2.5.5）が 44×44px。Apple の Human Interface Guidelines も 44pt を最小としている。高いほうに合わせた |
| 反応は 0.4 秒以内                  | ドハティの閾値。1982 年の IBM の研究で、反応が 400ms より速いと作業の効率が大きく上がるとされた                                                                            |
| Skeleton は 1 秒以上の読み込みだけ | サイトの注意点。1 秒未満で終わる処理に出すと、ちらついてかえって遅く感じる                                                                                                 |
| 長い値は 4 桁前後で区切る          | ミラーの法則（4±1 のまとまり）                                                                                                                                             |

## これからやること

- A の 10 個を、段階 1〜3 でトークンとコンポーネントに入れる。入れたら、上の表を更新する
- 機械でチェックできるものを増やす。Storybook の a11y チェックは、2026-10-18 に `test: "error"` にした（[docs/13](13-Base%20UI%20と%20Button.md)）。Oxlint の `jsx-a11y` プラグインを足すことを考える
- コンポーネントを作る手順がまとまったら、手順を SKILL にすることを考える
