# ダークモードを切り替える

記録日: 2026-10-18 / 対象: Base UI 1.9.0、Storybook 10.6.2

ヘッダーに、ライトとダークを切り替えるスイッチ（つまみが横に動く部品）を置いた。デザインシステムと CSS Modules で、配色の切り替えをどう表すかをまとめる。

## まとめ

- **部品の CSS は何も変えない。** `<html data-theme="dark">` を付けて、`color.css` で `color-scheme` を 1 つに決めるだけで、すべての部品が切り替わる
- 選んだ方を `localStorage` に保存し、`index.html` の小さな script で、画面を描く前に `<html>` に付ける
- 状態はライトとダークの 2 つ。何も選んでいないときは OS の設定に合わせる
- 切り替える部品は、Base UI の Switch を包んだ `ui/Switch`。オンのときがダークで、つまみに今の配色のアイコン（太陽か月）を出す。最初は Base UI の Toggle で作ったが、見た目がただのボタンだったので Switch に変えた
- 値の読み書きは React の `useSyncExternalStore` で書いた。zustand は入れていない
- Storybook の上のツールバーにも「配色」を足した。トークンのページにも効く

## 仕組み

```text
<html data-theme="dark">（スイッチで付ける。なければ OS の設定）
  ↓  :root[data-theme="dark"] { color-scheme: dark; }（color.css）
light-dark(明るい値, 暗い値) が、暗い値を選ぶ
  ↓
意味のトークン（--color-background など）が、すべて暗い値になる
  ↓
部品の CSS Modules（var(--color-primary) を使うだけ）
```

`color.css` に足したのは、これだけ。

```css
:root[data-theme="light"] {
  color-scheme: light;
}

:root[data-theme="dark"] {
  color-scheme: dark;
}
```

- `color-scheme: light dark`（両方）のときは、OS の設定で `light-dark()` の値が決まる（[docs/12](12-デザイントークン.md) の「ダークモード」）
- `color-scheme: dark`（1 つ）にすると、OS がライトでも `light-dark()` は暗い値を選ぶ
- `:root[data-theme="dark"]` は `:root` より詳細度が高いので、`data-theme` があればこちらが勝つ

部品は「今が明るいか暗いか」を知らない。知っているのは `--color-primary` という名前だけ。TS でいうと、部品はインターフェース（意味のトークン）にだけ依存していて、テーマの切り替えは根っこで実装を差し替えているだけ。React の Context を、一番外側の Provider から渡すのと同じ形になる。

[docs/14](14-TS%20の値で見た目を変える.md) の「アプリの状態は data 属性で伝える」と同じやり方でもある。違うのは、属性を付ける先が部品ではなく `<html>` で、受け取るのがトークンだというところ。

### 部品ごとに書き分けない

Base UI の docs の CSS Modules の例は、部品ごとに `@media (prefers-color-scheme: dark)` で暗い色を書いている。

```css
/* Base UI の docs の CSS Modules の例（一部） */
.Button {
  color: oklch(14.5% 0 0deg);

  @media (prefers-color-scheme: dark) {
    color: white;
  }
}
```

メディアクエリが見ているのは OS の設定だけなので、ページのスイッチでは上書きできない。スイッチに対応させるには、全部の部品に `[data-theme="dark"]` 用の書き方も足して、2 重に書くことになる。このリポジトリは色を全部トークンに寄せてあるので、この問題が起きない。

部品の CSS に書き分けを書かないように、Stylelint のルールを 2 つ足した（`stylelint.config.js`）。`tokens/` は検査しないので、`color.css` の `:root[data-theme]` は止まらない。

| ルール                                    | 止めるもの                              |
| ----------------------------------------- | --------------------------------------- |
| `media-feature-name-disallowed-list`      | `@media (prefers-color-scheme: …)`      |
| `selector-attribute-name-disallowed-list` | `[data-theme="dark"] .a` のような書き方 |

### 一部だけ暗くもできる

`color-scheme` は親から子に受け継がれる。部品の CSS で `color-scheme: dark` と書けば、その中だけ、いつも暗い配色にできる（ページの一部だけ暗い帯にする、など）。今は使っていない。

## 保存は `localStorage`

保存するのは、**自分で選んだ方**（`"light"` か `"dark"`）だけ。何も入っていなければ、OS の設定に合わせる。

| 置き場所                  | 持つもの                                 | TS でいうと            |
| ------------------------- | ---------------------------------------- | ---------------------- |
| `localStorage`            | 選んだ方。再読み込みしても、閉じても残る | ディスクの設定ファイル |
| `<html data-theme>`       | 今、画面に効いている方。CSS はここを読む | メモリ上の今の値       |
| OS の設定（`matchMedia`） | まだ何も選んでいないときの値             | 既定値                 |

`localStorage` は、ブラウザの中にある小さなキーと値の置き場。TS でいえば、ディスクに残る `Map<string, string>`。値は文字列だけで、オリジン（`http://localhost:5173` のような、スキーム・ホスト・ポートの組）ごとに分かれている。

### 流れ

1. **初めて開く**: `localStorage` は空なので、`data-theme` も付かない。`color-scheme: light dark` のままで、OS が決める
2. **スイッチを押す**: `<html data-theme="dark">` を付けると同時に、`localStorage` に `"dark"` を書く
3. **再読み込みする**: `index.html` の script が `localStorage` を読み、`"dark"` なら、画面を描く前に `data-theme="dark"` を付ける
4. **React のスイッチ**: `data-theme` を読んで、オンかオフかを決める

**保存を読むのは `index.html` の script だけ。** React の部品は `<html>` の属性だけを見る。値の流れが「`localStorage` → `<html>` → CSS と React」の一方向になるので、どちらが正しいか迷わない。

### ほかの保存先との比較

| 保存先                        | 残る期間                     | サーバーに送られるか       | 向いているもの                                                    |
| ----------------------------- | ---------------------------- | -------------------------- | ----------------------------------------------------------------- |
| **`localStorage`**            | 消すまで（そのブラウザだけ） | 送られない                 | 見た目の好み ← 今回                                               |
| `sessionStorage`              | タブを閉じるまで             | 送られない                 | そのときだけの状態                                                |
| Cookie                        | 期限まで                     | 毎回のリクエストで送られる | サーバーで HTML を作るとき（SSR）に、最初から正しい配色で返したい |
| サーバーの DB（ユーザーごと） | ずっと。別の端末でも同じ     | —                          | ログインがあって、端末をまたいで設定をそろえたい                  |

このアプリはブラウザだけで動く SPA で、サーバーで HTML を作らず、ログインもない。なので Cookie や DB を使う理由がない。

もう 1 つの理由は、`localStorage` がすぐに読める（同期）こと。読み終わるまで次に進まないので、画面を描く前の script で読める。IndexedDB のように後から結果が返ってくる（非同期の）置き場では、画面を描くのに間に合わない。

### よそでも同じやり方

有名なところの docs やソースを読んで確かめた。どこも `localStorage` に保存して、画面を描く前に読んでいた。

| どこ                                            | 保存先                                         | 画面を描く前に読む仕組み                        |
| ----------------------------------------------- | ---------------------------------------------- | ----------------------------------------------- |
| Tailwind CSS の docs（ダークモードの説明）      | `localStorage.theme`                           | 「`<head>` の中に直接書くのがいい」と書いてある |
| next-themes（Next.js 向けのテーマのライブラリ） | `localStorage` の `theme`                      | `<head>` に script を自動で差し込む             |
| shadcn/ui の docs（Vite でのダークモード）      | `localStorage` の `vite-ui-theme`              | なし。React の `useEffect` の中で付ける         |
| VitePress                                       | `localStorage` の `vitepress-theme-appearance` | script を差し込んで、ちらつきを防ぐ             |
| Docusaurus                                      | `localStorage`（保存しない設定もできる）       | —                                               |

違うのは、`<html>` に `class="dark"` を付けるか `data-theme="dark"` を付けるかくらい。next-themes も `data-theme` を付けるやり方だった。

shadcn/ui の Vite の例のように React の中で付けると、画面を描いた後に切り替わるので、再読み込みのたびに一瞬 OS の配色が見えることがある（下の「画面を描く前に付ける」）。

### 気をつけること

- **読み書きで例外が出ることがある**（ブラウザの設定で保存が止められているときなど）。`try/catch` で包み、読めなければ OS に合わせ、書けなくても今の画面は切り替える
- **中身は文字列で、開発者ツールから誰でも書き換えられる。** `"light"` か `"dark"` のときだけ使い、`"purple"` などは無視する。TS で、外から来た JSON を型で絞ってから使うのと同じ
- **キーにはプロジェクトの名前を付けた**（`design-system-prac-theme`）。`http://localhost:5173` は、ほかの Vite のプロジェクトとも同じオリジンになるので、`theme` だけだと重なる
- **キーは `src/constants/localStorage.ts` の `LOCAL_STORAGE_KEYS` にまとめた。** ページの URL（`PAGES`）や外部サイトの URL（`URLS`）と同じく、文字列を直接書かずにここから参照する。どんなキーを使っているかが 1 か所で分かり、プロジェクトの名前の付け忘れも見つけやすい
- **配色の値（`"light"`・`"dark"`）も、`src/constants/theme.ts` の `THEMES` にまとめた。** 型 `Theme` も `THEMES` から作るので（`(typeof THEMES)[keyof typeof THEMES]`）、配色を足すと型も増える。アプリの部品と Storybook のツールバー（`.storybook/preview.tsx`）が同じ値を使う。`index.html` の script と `color.css` の `:root[data-theme]` だけは import できないので、同じ文字列を書いてコメントで指している
- **ポートが違えば別の置き場になる。** アプリ（5173）と Storybook（6006）は、選んだ値を共有しない

## 画面を描く前に付ける

`index.html` の `<head>` に、ふつうの（`type="module"` ではない）script を書いた。

```html
<script>
  try {
    const theme = localStorage.getItem("design-system-prac-theme");
    if (theme === "light" || theme === "dark") {
      document.documentElement.dataset.theme = theme;
    }
  } catch {
    // 保存を読めないときは、OS の配色のままにする
  }
</script>
```

- `<head>` のふつうの script は、読み込んだその場で動き、終わるまで画面を描かない。なので、最初の 1 回目から正しい配色で描かれる
- React（`type="module"` の script）は、HTML を読み終えてから動く。React の中で `data-theme` を付けると、一瞬 OS の配色で描かれてから切り替わる。今回の作りでは、React は保存を読まないので、script がなければ選んだ値が使われない
- この script は `src/` の外なので、TS の定数を import できない。キーは `LOCAL_STORAGE_KEYS.THEME` と同じ文字列を書き、両方にコメントを付けた
- Vite は、`index.html` の中のふつうの script をそのまま `dist/index.html` に入れる。コメントも残る

## zustand を使わない理由

状態の保存に zustand を使うかも考えた。今回は使っていない。

- **値の置き場所は、もう 3 つある**（`localStorage`・`<html>`・OS の設定）。どれも zustand では代わりにならない。zustand の `persist` も、中では `localStorage` に書くだけ。zustand に入れると、同じ値の写しが 1 つ増えて、ずれないようにそろえる処理が要る
- **zustand では、ちらつきを防げない。** zustand はバンドルされた JS の中で動くので、画面を描く前に間に合わない。`index.html` の script は、zustand を入れても要る
- **読む部品が 1 つだけ。** CSS は `data-theme` を直接読むので、React で読むのはスイッチだけ。離れた部品どうしで値を分け合う場面がない
- **zustand の中身は、React の機能 1 つ。** zustand 5.0.15 のソースでは、`create` が返す hook は React の `useSyncExternalStore` を呼んでいるだけだった

zustand が向いているのは、離れた部品どうしで同じアプリの状態を読み書きするとき（サイドバーの開閉、カートの中身、通知の一覧など）。そういう機能を作るときに考える。

## `useSyncExternalStore`

React の外にある値を、React の state のように読むための hook。テーマはまさに「React の外にある値（`<html>` の属性と OS の設定）」の話なので、これで書いた。

```tsx
// features/Theme/ThemeToggle/hooks/useTheme.ts
export const useTheme = () => {
  const theme = useSyncExternalStore(subscribeTheme, getTheme);
  return [theme, setTheme] as const;
};

// features/Theme/ThemeToggle/index.tsx（useState と同じ形で使う）
const [theme, setTheme] = useTheme();
```

| 引数             | 役目                                                                                                      |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| `subscribeTheme` | 値が変わったら呼んでほしい関数（`onChange`）を受け取って登録する。**値は返さない。** 登録を外す関数を返す |
| `getTheme`       | **今の値**を返す。`<html data-theme>` があればそれ、なければ OS の設定                                    |

TS でいうと、RxJS の `BehaviorSubject`（`getValue()` で今の値、`subscribe()` で変化を受け取る）を React につなぐ形。

### 流れ

1. **最初の描画**: React が `getTheme()` を呼ぶ。これが初期値になる
2. **描画の後**: React が `subscribeTheme(onChange)` を呼ぶ。`onChange` は、React が用意した「値が変わったかもしれない」と伝える関数。これを 2 か所に登録する
   - `listeners`: スイッチを押したとき（`setTheme`）に呼ぶ
   - OS の配色の変化（`watchOsTheme`）: まだ選んでいないときは OS の配色に従うので、OS を変えたときにも呼ぶ
3. **スイッチを押した・OS を変えた**: `onChange` が呼ばれ、React が `getTheme()` を呼び直す。値が変わっていれば描き直す
4. **部品が消えるとき**: `subscribeTheme` が返した関数を React が呼んで、登録を外す

### 配色を「どれか」で書く

関数は、「ダークか？」ではなく「どの配色か（`Theme`）」を返す形にそろえた。

```ts
/** 今の配色。選んだ配色があればそれ、なければ OS の配色 */
const getTheme = () => {
  return getSelectedTheme() ?? getOsTheme();
};
```

| 関数                     | 返すもの・すること                                                                        |
| ------------------------ | ----------------------------------------------------------------------------------------- |
| `getSelectedTheme()`     | スイッチで選んだ配色（`<html data-theme>`）。まだ選んでいなければ `undefined`             |
| `getOsTheme()`           | OS の配色                                                                                 |
| `watchOsTheme(onChange)` | OS の配色が変わったら `onChange` を呼ぶ。登録を外す関数を返す                             |
| `isTheme(value)`         | `"light"` か `"dark"` なら `true`（型ガード）。属性の値はただの文字列なので、使う前に絞る |

つまみのアイコンも、`Record<Theme, ReactNode>` で配色ごとに引く。配色を足したら、アイコンも足さないと型エラーになる。

```tsx
const THEME_ICONS = {
  light: <SunIcon className={styles.sun} />,
  dark: <MoonIcon />,
} satisfies Record<Theme, ReactNode>;
```

「ダーク」を起点にしているのは、次の 2 か所だけ。どちらも、そうするしかない理由がある。

- **OS に聞くところ（`getOsTheme`）**: ブラウザには「この条件に当てはまるか」しか聞けない（`matchMedia("(prefers-color-scheme: dark)").matches`）。なので「ダークか」を聞いて、違えばライトとする。`prefers-color-scheme` の値は `light` と `dark` の 2 つだけで、どちらか一方だけが当てはまる（何も選んでいない人は `light`）。なので「ダークか」だけ聞けば、OS の配色が決まる
  - `OS_LIGHT_QUERY` も作って両方聞く形も考えたが、やめた。同じ質問を 2 回するだけになる。どちらにも当てはまらないとき（`prefers-color-scheme` に対応していない古いブラウザ）の「ライトとする」も、結局書くことになる。OS の設定を変えると 2 つの条件は同時に切り替わるので、両方を見張ると知らせが 2 回届く
- **スイッチ（`checked={theme === "dark"}`）**: スイッチの名前が「ダークモード」なので、オンがダーク

#### 経緯

1. 最初は `matchMedia(DARK_QUERY)` を、`subscribe` と `getTheme` の中に直接書いていた。`DARK_QUERY` が値なのか条件なのか、何を聞いているのかが読み取りにくかった
2. `isOsDarkMode()`・`watchOsDarkMode()` に分けた。読めるようにはなったが、コード全体が「ダークか」を起点にしていて、「今の配色はどれか」が見えにくかった
3. 「どの配色か」を返す `getOsTheme()`・`getSelectedTheme()` にして、`getTheme` を「選んだ配色 ?? OS の配色」の 1 行にした

#### OS の配色を直接聞く API

JS から OS の配色を読む方法は、今は `matchMedia` だけ。

| 方法                                                        | 状況                                                                                                                                             |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `window.matchMedia("(prefers-color-scheme: dark)").matches` | どのブラウザでも使える。MDN も、JS からメディアクエリを確かめる方法としてこれを紹介している                                                      |
| `navigator.preferences.colorScheme`（User Preferences API） | 実験中。Chrome 120 以降で、実験的な機能のフラグを有効にしたときだけ動く。Firefox と Safari は未対応（MDN の互換性データ、2026-10-19 に確かめた） |
| `Sec-CH-Prefers-Color-Scheme`                               | サーバーが受け取る HTTP のヘッダー。ブラウザの JS からは使えない                                                                                 |

`navigator.preferences` がどのブラウザでも使えるようになったら、`getOsTheme` の中だけを置き換えればよい。

### hook と utils に切り出した

最初は、配色の読み書き（約 80 行）と、スイッチの見た目（約 30 行）を、`ThemeToggle/index.tsx` の 1 つのファイルに書いていた。まず配色の読み書きを hook（`useTheme.ts`）に切り出し、そのあと hook の中を「React を使うかどうか」で `hooks/useTheme.ts` と `utils/theme.ts` に分けた。

| 目安                              | このとき                                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------ |
| 配色を使う部品が 2 つ目に増えたか | まだ。ただ、3 つの状態から選ぶ部品（下の「状態の数」）を作るなら、同じ読み書きを使う |
| 読み書きだけをテストしたいか      | 今は単体テストの仕組みがない                                                         |
| 1 つのファイルが読みにくいか      | 読みにくかった。読みにくいと感じたところは、ほとんどが読み書きの部分だった           |

- `ThemeToggle` は、`const [theme, setTheme] = useTheme()` から何を描くかだけになった
- 置き場所は、部品のフォルダの `hooks/` にした。今は `ThemeToggle` だけが使うため。最初は `features/Theme/` の直下に置いたが、使うのが 1 つの部品だけなので、部品のフォルダの中に移した。3 つの状態から選ぶ部品など、同じ機能のほかの部品でも使うようになったら `features/Theme/` の直下に、別の機能でも使うなら `features/` の外（`src/hooks/` など）に移す（[docs/06](06-コンポーネントの置き方.md)）
- 配色を選ぶ関数は、部品の中にあったときは `handleSetTheme` という名前だった。`handle` はイベントの受け手に付けることが多い名前なので、hook に移すときに `setTheme` にした
- 値は `<html data-theme>` にあるので、`useTheme` を使う部品がいくつあっても、同じ配色を指す。`setTheme` は登録された全員に知らせるので、どの部品も一緒に描き直される

#### hook と utils の分け方

hook の中の関数を、何に触るかで分けると、React を使うのは `useTheme` だけだった。

| 関数                                      | 何に触るか                             | React    |
| ----------------------------------------- | -------------------------------------- | -------- |
| `isTheme`                                 | 何にも触らない（純粋）                 | 使わない |
| `getOsTheme`・`watchOsTheme`              | OS の配色（`matchMedia`）              | 使わない |
| `getSelectedTheme`・`getTheme`            | `<html data-theme>`                    | 使わない |
| `listeners`・`subscribeTheme`・`setTheme` | `<html>`・`localStorage`・登録した相手 | 使わない |
| `useTheme`                                | 上の全部を React につなぐ              | **使う** |

- React を使わない関数を `utils/theme.ts` に、`useTheme` だけを `hooks/useTheme.ts` に置いた。単体テストは `utils/theme.ts` に当てる。関数を呼んで、`<html>` の属性・`localStorage`・登録した相手が呼ばれたかを見れば確かめられる
- `utils/theme.ts` から外に出すのは、`getTheme`・`subscribeTheme`・`setTheme` の 3 つだけ。`isTheme`・`getOsTheme`・`listeners` などは中だけで使う。テストのためだけに export すると、作りを変えるたびにテストも直すことになるので、この 3 つの動きを通して確かめる
- `useTheme` は 3 行で、中で動くのは React の `useSyncExternalStore` なので、単体テストは書かない
- これより細かく（「選んだ配色 ?? OS の配色」の判断だけを純粋な関数に）分けることもできるが、中身は `??` 1 つなので、分けても得るものが少ない
- `utils/theme.ts` は、状態（`listeners`）を持つ。ふつう `utils` には状態のない関数を置くことが多いので、`themeStore.ts` という名前も考えた。置き場所の決まり（React を使わない関数は `utils/`）に合わせて、`theme.ts` にした

## 状態の数

| 案                                           | よいところ                | 弱いところ                                                      |
| -------------------------------------------- | ------------------------- | --------------------------------------------------------------- |
| **ライトとダークの 2 つ**（今回）            | スイッチ 1 つで作れる     | 一度押すと「OS に合わせる」には戻せない（保存を消すしかない）   |
| 「OS に合わせる」「ライト」「ダーク」の 3 つ | OS に合わせる状態に戻せる | スイッチ 1 つでは作れない（Base UI の `ToggleGroup` や `Menu`） |

調べたところでは、3 つのほうが多かった。Tailwind CSS の docs の例は `localStorage.removeItem("theme")` で OS に合わせる状態に戻し、Docusaurus にも選んだ値を消して戻す関数がある。

まずは 2 つで作った。3 つに広げるときも、保存の仕組みはそのまま使える。`localStorage` の値を消して `data-theme` を外す操作を足すだけでよい。

## 切り替える部品

### Toggle から Switch に変えた

最初は Base UI の `Toggle`（押すたびに、押されている・いないが切り替わるボタン）で作った。月のアイコンのボタンで、押されているときがダーク。動きは正しかったが、見た目がただのボタンで、切り替えだと分かりにくかった。つまみが横に動く Base UI の `Switch` に変えた。

名前が紛らわしいので注意。Base UI では、横に動くほうが `Switch`、押したままになるボタンが `Toggle`。一般には、横に動くほうを「トグル（トグルスイッチ）」と呼ぶことも多い。Toggle の部品（`ui/Toggle`）は、使う場所がなくなったので消した。

名前は、どこでも使う部品は Base UI に合わせて `ui/Switch` にした。テーマを切り替える機能の部品は `ThemeToggle` にした。ここでの toggle は「切り替える」という動詞の意味で、ほかのプロジェクトでもよく見る名前。`ThemeSwitchToggle` も考えたが、Switch とトグルは同じ意味なので重なる。途中で一度 `ThemeSwitch` にしていたが、機能の部品の名前は Base UI の部品名と合わせなくてよいので、`ThemeToggle` に戻した。

フォルダは `features/Theme/ThemeToggle/` のまま、`Theme` の階層を残した。`features/<機能名>/<部品名>/` の決まり（[docs/06](06-コンポーネントの置き方.md)）で、`Theme` は部品ではなく機能の名前。依存の検査（`no-cross-feature`）も、`features/` の次のフォルダで機能を見分けている。3 つの状態の選択部品など、テーマの部品が増えたら同じフォルダに入れる。

| 案                                                         | 読み上げに伝わること                   | 見た目                                         |
| ---------------------------------------------------------- | -------------------------------------- | ---------------------------------------------- |
| **Base UI の `Switch`**（今回）                            | 「ダークモード」がオンかオフか         | つまみが横に動く。切り替えだと一目で分かる     |
| Base UI の `Toggle`（最初に作った）                        | 「ダークモード」が押されているかどうか | 押された見た目のボタン。ただのボタンに見える   |
| ふつうの Button で、名前を変える（「ライトモードにする」） | 押すと何が起きるか                     | 押すたびに名前が変わり、今どちらか分かりにくい |

- Switch は、Base UI が `role="switch"` と `aria-checked` を付けて、オンかオフかを伝える。そのため、**名前は状態で変えない**（「ダークモード」のまま）
- 文字を添えないので、`aria-label="ダークモード"` で名前を付けた（[docs/13](13-Base%20UI%20と%20Button.md) の「読み上げ」）
- Base UI の Switch.Root は、`<button>` ではなく `<span role="switch">` を描く（外側を `<label>` で包めるようにするため）。Tab で移れて、Space で切り替わることを確かめた

### つまみにアイコンを出す

見た目は 3 つの案から、つまみの中に今の配色のアイコン（ライトなら太陽、ダークなら月）を出す形にした。1 つの部品で済み、ヘッダーの幅を取らない。ほかの案は、Switch の両側に太陽と月を置く形と、「ダーク」の文字と並べる形。

`ui/Switch` は、ダークモード専用にしないため、つまみの中身を `thumbIcon` で受け取る。今の状態に合うアイコンは、使う側（`ThemeToggle`）が選んで渡す。

```tsx
<Switch
  aria-label="ダークモード"
  checked={theme === "dark"}
  onCheckedChange={(checked) => setTheme(checked ? "dark" : "light")}
  thumbIcon={theme === "dark" ? <MoonIcon /> : <SunIcon />}
/>
```

### 大きさ

新しい値は直接書かず、トークンから計算した（`Switch.module.css`）。

| もの     | 計算                                                    | 文字が 16px のとき |
| -------- | ------------------------------------------------------- | ------------------ |
| アイコン | `--size-icon`                                           | 20px               |
| つまみ   | アイコン + `--spacing-4`                                | 24px               |
| 溝の縦   | つまみ + 内側の余白（`--spacing-2` × 2）+ 枠（1px × 2） | 30px               |
| 溝の横   | つまみ × 2 + 内側の余白 + 枠                            | 54px               |

- 溝の横をつまみ 2 つ分にしたので、つまみが動く距離は、つまみ 1 つ分（`translate: var(--switch-thumb-size) 0`）になる
- Lucide のアイコンは、24 × 24 の枠の内側に余白を持って描かれている。なので、24px のつまみに 20px のアイコンを置いても、まわりがあいて見える
- `--size-icon` は em なので、Switch の文字の大きさ（`--font-size-16`）で決まる。置く場所の文字の大きさで変わらないように、Switch の CSS で文字の大きさを決めている

**押せる範囲**は、見た目の溝（30px）では縦が 44px に足りない。見えない `::after` を上下にはみ出させて、縦を `--size-touch-target`（44px）にした。`::after` は Switch の一部なので、そこを押しても Switch を押したことになる。溝の 6px 上を押すと切り替わり、30px 上では切り替わらないことを確かめた。

### 色

| 状態 | 溝                                     | つまみ               | つまみの中のアイコン                         |
| ---- | -------------------------------------- | -------------------- | -------------------------------------------- |
| オフ | `--color-input`（灰 420）              | `--color-background` | `--color-muted-foreground`（太陽はオレンジ） |
| オン | `--color-primary`                      | `--color-background` | `--color-primary`                            |
| 無効 | `--color-muted`。線は `--color-border` | `--color-border`     | `--color-muted-foreground`                   |

つまみは、オンでもオフでもページの背景の色（明るい配色なら白）にした。溝は塗りつぶし、オフは灰色、オンはメインの色。線は付けない。shadcn/ui の Switch と同じ形。

部品の形や状態を見分ける色は、3:1 以上にしたい（WCAG 1.4.11）。測った値は次のとおり（無効のときは、この決まりの外）。

| 比べるもの       | オフ・明るい | オン・明るい | オフ・暗い | オン・暗い |
| ---------------- | ------------ | ------------ | ---------- | ---------- |
| 溝とページの背景 | 3.03:1       | 11.1:1       | 5.74:1     | 6.14:1     |
| つまみと溝       | 3.03:1       | 11.1:1       | 5.74:1     | 6.14:1     |
| アイコンとつまみ | 8.45:1       | 11.1:1       | —          | 6.14:1     |

- つまみがページの背景の色なので、「溝とページの背景」と「つまみと溝」は同じ組になる。溝の色を、ページの背景に対して 3:1 以上にすれば、両方が満たせる
- オフの溝に使う `--color-input` を `color.css` に足した。名前は shadcn/ui に合わせた（shadcn/ui も、入力欄の枠とオフの Switch の溝に `input` を使う）。`--color-border`（飾りの線、灰 200）は、ページの背景に対して 1.61:1 しかなく、溝の形が見えない
- `--color-input` は灰 420。明るい背景に対して 3:1 を守れる、いちばん薄い灰色（3.03:1。ひとつ薄い灰 400 は 2.85:1 で足りない）。暗い背景にも 5.74:1 あるので、どちらの配色でも同じ値にした
- オンの溝はメインの色にした。ヘッダーの中で、ほかにメインの色で目立たせているものはない（`.claude/rules/ux.md` の「見た目の強弱」）
- つまみの移動と色の切り替えは 150ms でなめらかにする。動きを減らす設定の人には、なめらかにしない（その場で切り替わる）

#### 色を決めるまで

| 試した形                                           | やめた理由・選んだ理由                                                     |
| -------------------------------------------------- | -------------------------------------------------------------------------- |
| 1. 溝はページの背景の色に濃い線、つまみは濃い灰色  | 太陽をオレンジにすると、灰色のつまみの上の太陽がくすんで見えた             |
| 2. 溝を灰 500 で塗り、つまみは白                   | 灰色が濃く、重く見えた                                                     |
| 3. 溝はごく薄い灰色で塗り、溝とつまみに灰 500 の線 | 線が 2 重になって、にぎやかに見えた                                        |
| **4. 溝を灰 420 で塗り、つまみは白**（今）         | 塗りだけで 3:1 を守れる、いちばん薄い灰色。形は 2 と同じで、少し軽くなった |

灰 420 でもまだ濃く見えた。ただ、これより薄い灰色は、白いつまみと溝の差が 3:1 を下回る（灰 400 は 2.85:1、灰 300 は 2.1:1、灰 200 は 1.61:1）。弱視の人に、つまみの位置が分かりにくくなる。

ヘッダーのスイッチなら、オレンジの太陽やページ全体の配色でも状態が分かる。でも `ui/Switch` は、アイコンのない設定にも使う部品なので、それには頼れない。軽さより 3:1 を取って、灰 420 のままにした。

`vp test` の a11y のチェック（axe）は、文字のコントラストしか見ない。部品の形や状態の 3:1（WCAG 1.4.11）を下回っても、テストは通ってしまう。なので、ここは手で測って確かめている。

### 太陽のアイコンをオレンジにした

ヘッダーのスイッチだけ、太陽のアイコンをオレンジにした。`color.css` に、意味のトークン `--color-sun` を足した。

```css
--color-sun: light-dark(var(--color-primitive-orange-600), var(--color-primitive-orange-400));
```

- 部品の色は、意味のトークンだけを使う決まり（色の材料の `--color-primitive-orange-*` は、部品からは使えない。Stylelint が止める）。なので、使い道の名前を付けたトークンを足した
- オレンジの意味のトークンには `--color-warning`（注意の文字、橙 800）もあるが、役目が違う。太陽に使うと、後で注意の色を変えたときに太陽の色まで変わってしまう
- 太陽を載せる先は、つまみ（`--color-background`）。つまみに対して 3:1 以上になる中で、いちばん鮮やかなオレンジを選んだ

| オレンジ   | 明るい配色のつまみ（白）に対して | 暗い配色のつまみ（灰 900）に対して |
| ---------- | -------------------------------- | ---------------------------------- |
| **橙 400** | 2.3:1                            | **7.58:1**（暗い配色で使う）       |
| 橙 500     | 2.67:1                           | 6.53:1                             |
| **橙 600** | **3.18:1**（明るい配色で使う）   | 5.47:1                             |
| 橙 700     | 3.88:1                           | 4.48:1                             |
| 橙 800     | 4.85:1                           | 3.59:1                             |

- 太陽が出るのはライトのときだけなので、ヘッダーで実際に見えるのは橙 600 だけ。暗い配色の値は、ストーリーなどで暗い配色の中に太陽を置いたときのために決めた
- 最初は濃い灰色のつまみに合わせて橙 400 にしていた。つまみを白にしたので、白に対して 3:1 を超える橙 600 に変えた
- 色を付けるのは `ThemeToggle` の CSS（`.sun { color: var(--color-sun); }`）。Lucide は `currentColor` で描くので、`<SunIcon className={styles.sun} />` の `color` を変えると線の色が変わる。`ui/Switch` は、つまみの中のアイコンの色を決めない（使う側が色を付けなければ、`--color-muted-foreground` で描く）

## Storybook の配色

上のツールバーに「配色」（OS に合わせる・ライト・ダーク）を足した。OS の設定を変えずに、部品とトークンのページを暗い配色で確かめられる。

```ts
globalTypes: {
  theme: {
    description: "配色",
    toolbar: {
      title: "配色",
      icon: "mirror",
      items: [
        { value: "os", title: "OS に合わせる", icon: "browser" },
        { value: "light", title: "ライト", icon: "sun" },
        { value: "dark", title: "ダーク", icon: "moon" },
      ],
      dynamicTitle: true,
    },
  },
},
initialGlobals: { theme: "os" },
```

選んだ値は `globals.theme` に入る。それを、アプリと同じく `<html data-theme>` に付ける。付ける場所が 2 つ要った。

| 付ける場所                                           | 効くところ                                              | 効かないところ                                      |
| ---------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------- |
| decorator（ストーリーを描くたびに動く）              | 部品のストーリー、`vp test`、ストーリーごとの `globals` | トークンのページ（ストーリーのない MDX）            |
| Storybook の通知（`SET_GLOBALS`・`GLOBALS_UPDATED`） | トークンのページ、部品のストーリー                      | `vp test`（Storybook の画面を開かないので届かない） |

- 最初は decorator だけにした。ツールバーはトークンのページにも出るのに、選んでも何も変わらなかった。decorator はストーリーを描くときにしか動かないため
- そこで、`addons.getChannel()` で「globals が変わった」という通知も受け取るようにした。`SET_GLOBALS` は開いたとき、`GLOBALS_UPDATED` は選び直したときに届く
- 通知だけにして decorator を外すと、`vp test` の中では配色が付かなかった（`data-theme` が `undefined`）。なので両方残している
- 通知のイベント名は `storybook/internal/core-events` から import している。`internal` は、アドオンを作る人向けの API で、Storybook を上げたときに変わることがある。壊れても、効かなくなるのはトークンのページの切り替えだけ

ストーリーに `globals: { theme: "dark" }` と書くと、そのストーリーだけ暗い配色になる（`UI/Switch` の `CheckedInDark`）。`vp test` の a11y のチェックも、暗い配色で行われる。Toggle で作っていたときのストーリー（`PressedInDark`、仕組みは同じ）に一時的なチェックを足して、`vp test` の中で `data-theme` が `dark`、背景が `rgb(26, 26, 26)` になっていることを確かめた。

### アドオンは入れなかった

Storybook には、テーマを切り替えるアドオン（`@storybook/addon-themes`）がある。10.6.2 のソースを読むと、`withThemeByDataAttribute` は decorator の中で `<html>` に属性を付けるだけだった。同じことは数行で書けて、decorator なのでトークンのページで効かないのも同じ。依存を増やさずに、Storybook 本体の機能（`globalTypes` と decorator）で書いた。

## 確かめたこと

アプリ（`vp dev`）で、Playwright で確かめた。

| 場面                                | `data-theme` | スイッチ | つまみ | 保存       | ページの背景      |
| ----------------------------------- | ------------ | -------- | ------ | ---------- | ----------------- |
| OS がライト、まだ選んでいない       | なし         | オフ     | 太陽   | なし       | 白                |
| スイッチを押した                    | `dark`       | オン     | 月     | `"dark"`   | `rgb(26, 26, 26)` |
| 再読み込みした                      | `dark`       | オン     | 月     | `"dark"`   | `rgb(26, 26, 26)` |
| キーボード（Space）でライトに戻した | `light`      | オフ     | 太陽   | `"light"`  | 白                |
| OS がダーク、まだ選んでいない       | なし         | オン     | 月     | なし       | `rgb(26, 26, 26)` |
| 開いたまま OS をライトに変えた      | なし         | オフ     | 太陽   | なし       | 白                |
| OS がダークで、ライトを保存している | `light`      | オフ     | 太陽   | `"light"`  | 白                |
| 保存が `"purple"`（OS はダーク）    | なし         | オン     | 月     | `"purple"` | `rgb(26, 26, 26)` |

- 幅 320px でも、ヘッダーは横にはみ出さない（ロゴの下に、ナビゲーションとスイッチが折り返す）
- ビルドしたアプリ（`vp run build` → `vp preview`）で、React を含む JS を読み込ませずに開いた。`"dark"` を保存していると、React が動いていなくても `data-theme="dark"` が付き、背景が暗くなった。`index.html` の script だけで、画面を描く前に間に合っている
- Storybook で、トークンのページ（Color）でツールバーから選び直すと、`data-theme` が切り替わった。ストーリーで暗い配色にしたもの（Toggle のときの `PressedInDark`）からトークンのページに移ると、ツールバーの値（OS に合わせる）に戻った

## つまずいたこと: 新しい import の後の `vp test`

新しい import（`@base-ui/react/toggle`、`storybook/internal/core-events`）を足した後の 1 回目の `vp test` が、テストを読み込めずに失敗した（`Failed to fetch dynamically imported module`、`Vitest failed to find the current suite`）。何も変えずにもう一度動かすと通った。後で `@base-ui/react/switch` を足したときは、1 回目から通った。Vite が新しい依存を見つけて、依存の事前の変換をやり直したためだと思われる（確かめてはいない）。

## 残っていること

- 「OS に合わせる」に戻す手段（3 つの状態にする）
- 別のタブで切り替えたときに、開いているほかのタブも合わせる（`storage` イベント）
- 暗い配色での影（[docs/12](12-デザイントークン.md) の「暗い配色では影がほとんど見えない」）
- `vp test` で、すべてのストーリーを暗い配色でも検査する（今は `CheckedInDark` だけ）
- 右から左に書く言語（RTL）では、つまみの動く向きを逆にする（今は日本語だけなので、右に動くだけ）
