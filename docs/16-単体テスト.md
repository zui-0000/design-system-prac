# 単体テスト

記録日: 2026-10-19 / 対象: Vite+ 1.1.0（Vitest 5.0.3）、jsdom 30.1.3、Testing Library（React 16.3.3）

`vp test` で、2 種類のテストが動く。単体テスト（`unit`）は 2026-10-19 に足した。

| プロジェクト | 何を確かめるか                                         | どこで動くか                             | 対象のファイル        |
| ------------ | ------------------------------------------------------ | ---------------------------------------- | --------------------- |
| `storybook`  | ストーリーが壊れずに表示されるか、a11y の違反がないか  | Playwright の Chromium（本物のブラウザ） | `*.stories.tsx`       |
| `unit`       | React を使わない関数（`utils/`）や hook が正しく動くか | Node の上の jsdom（ブラウザの真似）      | `src/**/*.test.ts(x)` |

```zsh
vp test                       # 両方
vp test --project unit        # 単体テストだけ
vp test watch --project unit  # 保存するたびに、単体テストだけを動かし直す
```

Chromium は必ず入れる。`vp test` 1 つで、ストーリーのテストと単体テストの両方を動かすため。

入れ忘れないように、`package.json` の `prepare` で、`vp install` のたびに入れる。

```jsonc
"prepare": "vp config && playwright install chromium"
```

`prepare` は、`vp install`（中で動く `pnpm install`）の最後に動くスクリプト。npm の決まりで、名前で動くタイミングが決まっている。Gradle で言えば、依存を入れるタスクに `finalizedBy` で、終わったら必ず動くタスクをつなぐのに近い。

| 試したこと                                                | 結果                                                                                     |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| ブラウザが入っている状態で `playwright install chromium`  | 0.4 秒で終わる。ダウンロードしない。ネットにつながっていなくても通る                     |
| クローンし直して、ブラウザの無い状態で `vp install`       | Chromium・ヘッドレス版・ffmpeg（約 570MB）を入れ、1 分 36 秒かかった。`vp test` は通った |
| クローンし直して、ネットにつながらない状態で `vp install` | `Failed to download` で、`vp install` ごと失敗した                                       |
| 依存が変わっていない状態で `vp install`                   | `Already up to date` で終わり、`prepare` は動かなかった                                  |

- 最初の `vp install` はダウンロードを待つが、2 回目からは入っているのでほぼ待たない
- ネットにつながらないと、最初の `vp install` は失敗する。依存のパッケージは pnpm の置き場にあれば入るので、ブラウザのせいで止まることになる。つながってから入れ直せばよい
- ブラウザだけを消したときは、`vp install` では入らない（`prepare` が動かない）。`vp exec playwright install chromium` を手で実行する
- `package.json` の `scripts` を書き換えただけでは、`vp install` は `Already up to date` で終わった。`prepare` が動くのは、依存を入れる作業があるとき（クローンした直後、lockfile が変わったときなど）

### 入るのはブラウザそのもので、ChromeDriver ではない

`playwright install chromium` は、ブラウザの本体を落とす。ChromeDriver は入らない（置き場に `chromedriver` という名前のファイルは無かった）。

| 置き場（`~/Library/Caches/ms-playwright/`） | 中身                                                                                       |
| ------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `chromium-1248/`                            | `Google Chrome for Testing.app`（テスト用に配られている Chrome。画面を出して動かすとき用） |
| `chromium_headless_shell-1248/`             | `chrome-headless-shell`（画面を出さない版。`vp test` の `headless: true` はこちらで動く）  |
| `ffmpeg-1013/`                              | 動画を書き出す道具。テストの様子を録画するときに使う                                       |

`1248` は、Playwright が決めているブラウザの版の番号。Playwright 1.64.0 は、Chrome for Testing 156.0.8078.4 を使う（落とせなかったときのエラーに出た）。Playwright を上げると、合う番号のブラウザを入れ直すことになる。

ChromeDriver が要らないのは、ブラウザとのつなぎ方が違うため。

| 道具                                       | ブラウザとのつなぎ方                                                                                                   |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Selenium・WebdriverIO                      | WebDriver（W3C の決まり）で、ChromeDriver に頼む。ChromeDriver が、ブラウザに伝え直す                                  |
| Playwright（`@vitest/browser-playwright`） | ブラウザを自分で起動し、Chrome DevTools Protocol（CDP。Chrome の開発者ツールが使う仕組み）で直接話す。間に何も挟まない |

Playwright の中を見ると、ブラウザを `--remote-debugging-pipe`（CDP をパイプでつなぐ起動の仕方）で起動している。TS で言えば、ChromeDriver は「DB の前に置いた REST の中継サーバー」、CDP は「DB のドライバーで直接つなぐ」に近い。

Vitest のブラウザモードは、WebdriverIO でも動かせる（`@vitest/browser-webdriverio`）。そちらにすると ChromeDriver を使う。このリポジトリは Playwright を使っている。

入れていない状態（`PLAYWRIGHT_BROWSERS_PATH` を空のフォルダにした）では、`vp test` が storybook のプロジェクトで `Executable doesn't exist` になり、通らなかった（`--project unit` だけなら通った）。最初は「単体テストだけなら入れなくてよい」と README に書いたが、`vp test` で両方を動かす形にそろえるため、必ず入れることにした（2026-10-19）。

## 入れたパッケージ

```zsh
vp add -D -E jsdom@30.1.3 @testing-library/react@16.3.3 @testing-library/dom@10.4.2 @testing-library/jest-dom@7.0.1 @testing-library/user-event@14.6.8
```

| パッケージ                    | 役目                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------ |
| `jsdom`                       | Node の上で、`document`・`localStorage` などのブラウザの仕組みを真似る                     |
| `@testing-library/react`      | 部品を描いたり（`render`）、hook を動かしたり（`renderHook`）する                          |
| `@testing-library/dom`        | 描いたものを、役割や文字で探す（`screen.getByRole`）。上の `react` が使う                  |
| `@testing-library/jest-dom`   | `toBeInTheDocument()`・`toHaveAttribute()` など、DOM を確かめる `expect` を足す            |
| `@testing-library/user-event` | クリックやキー入力を、人が操作したときと同じ順番のイベントで起こす（`fireEvent` より近い） |

- `@testing-library/react` は 16 から、`@testing-library/dom` を自分では持たず、使う側に入れてもらう形（peer 依存）になった。だから別に入れる。TS で言えば、`@types/react` を使う側が入れるのと同じ
- どれも `-E` で、`^` の付かない決まったバージョンにした（バージョンは自分で上げる決まり）
- Vitest のブラウザモードの部品（`@vitest/browser-preview`）が使っていた `user-event` も、14.6.7 から 14.6.8 にそろった（パッチ版）。ストーリーのテストは、そろったあとも通った

## jsdom にした理由

単体テストを動かす場所は、jsdom と、ストーリーのテストと同じブラウザモード（本物の Chromium）から選べた。

|              | jsdom                                                           | ブラウザモード       |
| ------------ | --------------------------------------------------------------- | -------------------- |
| 動く場所     | Node の上。ブラウザの仕組みを JS で真似る                       | 本物のブラウザ       |
| 速さ         | 2 回目からは 1 秒かからなかった（初回は jsdom の準備で 6.5 秒） | ブラウザの起動を待つ |
| 本物との違い | 真似なので、無いものがある（下の `matchMedia`）                 | 本物と同じ           |
| 準備         | パッケージを入れるだけ                                          | Chromium が要る      |

`utils/` の関数は、`<html>` の属性や `localStorage` を読み書きするだけなので、真似で足りる。速く動けば、保存のたびに動かし直しても待たない。

Kotlin + Spring で言えば、jsdom は MockMvc（サーバーを立てずに、Spring MVC の仕組みだけで Controller を呼ぶ）、ブラウザモードは `@SpringBootTest(webEnvironment = RANDOM_PORT)`（本当にサーバーを立てる）に近い。

### jsdom に無いもの

jsdom には `window.matchMedia` が無い（`typeof window.matchMedia` が `"undefined"` になった）。`utils/theme.ts` は `matchMedia` で OS の配色を読むので、テストでは偽物を用意する。`localStorage` はある（`setItem` した値を `getItem` で読めた）。

## 設定

`vite.config.ts` の `test.projects` に、`unit` のプロジェクトを足した。

```ts
test: {
  projects: [
    {
      extends: true,
      test: {
        name: "unit",
        include: ["src/**/__tests__/**/*.test.{ts,tsx}"],
        environment: "jsdom",
        globals: true,
        setupFiles: ["./src/__setup__/setup.ts"],
      },
    },
    {
      extends: true,
      plugins: [storybookTest({ ... })],
      test: { name: "storybook", browser: { ... } },
    },
  ],
},
```

`projects` は、1 つの設定ファイルで、設定の違うテストをいくつも動かす仕組み。Gradle で言えば、`test` のタスクを 2 つ作り、片方は単体テスト、片方は結合テストを動かすのに近い。

### プロジェクトの中に書く

Vitest 5 では、`projects` に書いたプロジェクトは、上（`test` の直下）の設定を引き継ぐ（`extends: true` が既定）。`include` などを上に書くと、storybook のプロジェクトにも入ってしまう。

わざと `include` を上に書くと、storybook のプロジェクトでは無視されて、警告が出た。

```
Warning: Starting in Storybook 8.5.0-alpha.18, the "test.include" option in Vitest is discouraged in favor of just using the "stories" field in your Storybook configuration.
The values you passed to "test.include" will be ignored, please remove them from your Vitest configuration where the Storybook plugin is applied.
```

storybook のプロジェクトは、`.storybook/main.ts` の `stories` から、動かすファイルを自分で決める。だから `include`・`environment`・`globals`・`setupFiles` は、`unit` のプロジェクトの中だけに書いた。

`extends: true` は既定なので書かなくても同じだが、storybook のプロジェクトに合わせて書いた。引き継ぐのは、`resolve.alias`（`~/`）と、`plugins`（React Compiler など）。テストでも `~/` から import できる。

### describe・test・expect を import せずに使う（`globals: true`）

```ts
// globals: false（既定）
import { describe, expect, test } from "vite-plus/test";

// globals: true
describe("…", () => { … }); // import が要らない
```

もう 1 つ、Testing Library の片付けが自動になる。Testing Library は、`afterEach` がグローバルにあるときだけ、テストごとに描いたものを消す（`cleanup`）。`globals: false` だと `afterEach` がグローバルに無いので、自分で `afterEach(cleanup)` を書くことになる。

1 つ目のテストで描いたあと、2 つ目のテストの始めに `document.body` を見ると、空になっていた。

### 前に読むファイル（`src/__setup__/setup.ts`）

```ts
import "@testing-library/jest-dom/vitest";
```

`setupFiles` に書いたファイルは、テストのファイルごとに、テストの前に読まれる。ここで 1 回 import すれば、どのテストでも `toBeInTheDocument()` などが使える。

フォルダの名前は、テストのためだけのフォルダだと分かるように、`__` で囲んだ（Jest の `__mocks__` などと同じ）。

### tsconfig を分ける

`globals: true` にしても、型は自動では付かない。`vite-plus/test/globals`（Vitest の `vitest/globals` に当たる）を `types` に足す。ただし、アプリのコードには足さず、テストのファイルにだけ読ませるため、tsconfig を分けた。

```text
tsconfig.json          … 下の 3 つを指すだけ（files: []）
├── tsconfig.app.json  … アプリのコード（__tests__/ と src/__setup__/ は exclude で外す）
├── tsconfig.test.json … __tests__/ と src/__setup__/（app を extends して、types を足す）
└── tsconfig.node.json … vite.config.ts と .storybook/main.ts
```

```jsonc
// tsconfig.test.json
{
  "extends": "./tsconfig.app.json",
  "compilerOptions": {
    "tsBuildInfoFile": "./node_modules/.tmp/tsconfig.test.tsbuildinfo",
    "types": ["vite/client", "vite-plus/test/globals"]
  },
  "include": ["src/**/__tests__", "src/__setup__"],
  "exclude": []
}
```

アプリのコードにも `vite-plus/test/globals` を足すと、アプリのコードに `expect` を書いても型エラーにならない。動かすと `expect is not defined` で落ちる。分けておけば、型チェックで止まる。

Gradle で言えば、JUnit を `testImplementation` で入れるのと同じ。`src/test` からは見えて、`src/main` からは見えない。

- `exclude: []` は、`tsconfig.app.json` の `exclude`（テストのファイルを外す）を引き継がないために書く。`extends` は `exclude` も引き継ぐので、書かないとテストのファイルが外れたままになる。消して `tsc -b` を動かすと、`TS18003: No inputs were found in config file`（読むファイルが 1 つも無い）になった
- `tsBuildInfoFile` は、`tsc -b` が前回の結果を残すファイル。app と同じ場所にすると上書きし合うので、別の名前にする

## 確かめたこと

一時的なテストのファイルを置いて確かめ、確かめたあとに消した。

| 確かめたこと                                                                            | 結果                                                                            |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| テストのファイルで、import せずに `describe`・`test`・`expect` を使う                   | 通る                                                                            |
| 部品を描いて、jest-dom の `toBeInTheDocument()`・`toHaveAttribute()` で確かめる         | 通る                                                                            |
| テストのファイルで `~/constants/theme` を import する                                   | 通る                                                                            |
| アプリのコード（`src/leak.ts`）で `expect` を使う                                       | `vp check` と `tsc -b` の両方で `TS2304: Cannot find name 'expect'`             |
| テストのファイルに型の間違いを入れる                                                    | `vp check` と `tsc -b` の両方で `TS2322`（`tsconfig.test.json` が読まれている） |
| jest-dom に無い `toBeInTheDocumentX()` を書く                                           | `TS2551`（jest-dom の型が効いている）                                           |
| 1 つ目のテストで描いたあと、2 つ目のテストで `document.body` を見る                     | 空（自動で片付いた）                                                            |
| `vp test`                                                                               | ストーリーは `storybook` だけで、`*.test.tsx` は `unit` だけで動いた            |
| `vp run lint:deps`                                                                      | テストのファイルと `src/__setup__/` も、依存の検査の対象に入った                |
| `utils/__tests__/`・`ui/Button/__tests__/`・`constants/__tests__/` に置き、`../` で読む | `vp check` も `vp test` も通る                                                  |
| `__tests__/` の外（`utils/x.test.ts`）に置く                                            | `vp test` では動かず、`vp check` と `tsc -b` で `TS2593`・`TS2304`              |
| `__tests__/` から `../../index` を読む                                                  | `vp check` の lint で止まる（`no-restricted-imports`）                          |

## テストの書き方の決まり

- 確かめるファイルと同じ階層に `__tests__/` を作り、その中に `<名前>.test.ts` で置く。部品を描くなら `.test.tsx`。`__tests__/` は、テストを書くときに作る
- 確かめるファイルは `../` で読む（`../theme`）
- `it` ではなく `test` を使う。名前は日本語で「〜の場合、〜すること」
- `describe`・`test`・`expect`・`vi` は import しない
- テストのためだけに export しない。外に出した関数の動きを通して確かめる（[docs/15](15-ダークモードを切り替える.md) の「hook と utils の分け方」）

```text
ThemeToggle/
├── index.tsx
├── hooks/
│   └── useTheme.ts
└── utils/
    ├── theme.ts
    └── __tests__/
        └── theme.test.ts   import { getTheme } from "../theme";
```

置き方は 3 つ考えられる。

| 置き方                                       | 例                                  | 良いところ                               | 気になるところ                                         |
| -------------------------------------------- | ----------------------------------- | ---------------------------------------- | ------------------------------------------------------ |
| ファイルのすぐ隣                             | `utils/theme.test.ts`               | 一番近い。import は `./theme`            | フォルダの中で、ソースとテストが交互に並ぶ             |
| 同じ階層の `__tests__/`（これにした）        | `utils/__tests__/theme.test.ts`     | 近いまま、ソースとテストの一覧が分かれる | import が `../theme` になる                            |
| 別の木（Kotlin の `src/main` と `src/test`） | `test/components/.../theme.test.ts` | ソースの木にテストが混ざらない           | 遠い。ファイルを動かすと、テストも別に動かすことになる |

`__tests__/` は、Jest が最初からテストのフォルダとして探す名前（Jest の `testMatch` の既定）で、JS ではよく見る置き方。Vitest は名前の決まりが違い、`*.test.ts` だけを探すので、`__tests__/` の中でも `.test.ts` を付ける。

### `__tests__/` の外に置くと止まる

`__tests__/` の外に置いたテストは、`unit` のプロジェクトの `include` に入らないので動かない。動かないことに気づけないと困るので、型チェックで止まるようにした。

- `tsconfig.test.json` は `__tests__/` だけを読み、`tsconfig.app.json` は `__tests__/` を外す
- `__tests__/` の外のテストは、アプリのコードとして型チェックされる。アプリのコードには `describe`・`test`・`expect` の型が無いので、エラーになる

```
x typescript(TS2593): Cannot find name 'test'. Do you need to install type definitions for a test runner? …
x typescript(TS2304): Cannot find name 'expect'.
```

`vp check` が止まるので、コミットも止まる。`__tests__/` の中に、テストのための小さな関数（偽物を作る関数など）を置いても、テストと同じ型で読まれる。

### `__tests__/` から `../` を 1 つ許す

`../` は、原則 lint で止めている（[docs/09](09-import%20のパス.md)）。`__tests__/` から確かめるファイルを読むには 1 つ上がるので、`hooks/`・`utils/` と同じく、`vite.config.ts` の lint の `overrides` に `src/**/__tests__/**` を足して、`../` を 1 つだけ許した。`../../` は止まる。

## 残っていること

- `utils/__tests__/theme.test.ts` を書く。`matchMedia` の偽物を用意する
