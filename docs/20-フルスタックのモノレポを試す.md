# フルスタックのモノレポを試す

記録日: 2026-10-21 / 対象: Vite+ 1.3.0、pnpm 12.14.0、oRPC 1.15.7、zod 4.6.7、MSW 3.0.3、Hono 4.13.13、Bun 1.4.3、React 19.3.1

デザインシステムを作るのと並行して、フロントエンドの実装も学ぶ。いずれ、Vite+ のモノレポで、React と Hono と oRPC のフルスタック TS を組む（[docs/01](01-学習の進め方.md) の「卒業したら、お題に沿って画面を作る」）。このリポジトリには作らず、使い捨ての環境（Claude の scratchpad）で、組めるかを試した。

## 試した構成

```text
mono/
├── vite.config.ts          lint・整形・キャッシュの設定（全体で 1 つ）
├── pnpm-workspace.yaml     apps/*, packages/*
├── apps/
│   ├── web/                React。oRPC のクライアントと、MSW の偽物の API
│   └── api/                Hono + oRPC。約束を実装した本物の API。Bun で動かす
└── packages/
    ├── contract/           oRPC の約束（zod のスキーマ）。web と api の両方が読む
    └── ui/                 CSS Modules の Button。web が読む
```

ひな形は `vp create vite:monorepo` で作り、中のサンプル（`apps/website`・`packages/utils`）を消して組んだ。

## 結果

| 確かめたこと                                                     | 結果                                 |
| ---------------------------------------------------------------- | ------------------------------------ |
| `packages/contract` を、ビルドせずに TS のまま読ませる           | 通った                               |
| `packages/ui` の CSS Modules を、`apps/web` がそのまま使う       | 通った（開発サーバーでもビルドでも） |
| MSW で、約束どおりの偽物の API を返す（ブラウザと jsdom の両方） | 通った（jsdom は 1 か所つまずいた）  |
| `apps/api`（Hono + oRPC）が、同じ約束を実装して動く              | 通った                               |
| 約束を破ると、ルートの `vp check` が型エラーで止める             | 止めた                               |

### 約束（contract）を真ん中に置く

```ts
// packages/contract/src/index.ts
export const CardSchema = z.object({ id: z.number(), title: z.string() });

export const contract = {
  card: {
    list: oc.output(z.array(CardSchema)),
    delete: oc.input(z.object({ id: z.number() })).output(z.object({ ok: z.boolean() })),
  },
};
```

```jsonc
// packages/contract/package.json
"exports": { ".": "./src/index.ts" }   // ビルドせず、TS のまま渡す
```

- web は約束の**型だけ**を読んで、クライアントを作る（`ContractRouterClient<typeof contract>`）。サーバーの実装は読まない
- web の本番のビルドには、zod も約束のスキーマも入らなかった（型だけを `import type` で読んでいるため）
- api と、web の偽物の API（MSW）は、どちらも `implement(contract)` で約束を実装する。返す値の形がずれると型エラーになる
- 入力は、実行時にもスキーマで確かめる。約束にない入力（`{ id: "x" }`）を本物の API に送ると、`Input validation failed` で弾かれた

わざと壊して、ルートの `vp check` で確かめた。

| 壊し方                                        | 結果                                                               |
| --------------------------------------------- | ------------------------------------------------------------------ |
| 偽物の API が `title: 2`（数字）を返す        | `TS2322: Type 'number' is not assignable to type 'string'`         |
| web が、約束にない `orpc.card.lists()` を呼ぶ | `TS2551: Property 'lists' does not exist ... Did you mean 'list'?` |

### 偽物の API は、約束を実装して MSW に載せる

```ts
// apps/web/src/mocks/handlers.ts
const os = implement(contract);
const router = os.router({
  card: {
    list: os.card.list.handler(() => cards),
    delete: os.card.delete.handler(({ input }) => { … }),
  },
});
const rpcHandler = new RPCHandler(router);

export const handlers = [
  http.all("*/rpc/*", async ({ request }) => {
    const { matched, response } = await rpcHandler.handle(request, { prefix: "/rpc" });
    return matched ? response : undefined;
  }),
];
```

oRPC の通信の形式を自分で真似せず、oRPC のサーバーの部品（`RPCHandler`）を MSW の中で動かした。偽物も本物と同じく約束を実装するので、約束を変えると、偽物も直すまで型エラーになる。

### MSW 3 は Vite の plugin で動かす

MSW 3（2026-09-28）は、Vite の plugin（`msw/vite`）を持つ。

```ts
// apps/web/vite.config.ts
plugins: [react(), msw()],

// apps/web/src/main.tsx
if (import.meta.env.DEV) {
  const { network } = await import("virtual:msw");
  const { handlers } = await import("./mocks/handlers");
  network.configure({ handlers });
  await network.enable();
}
```

- 開発サーバーが `mockServiceWorker.js` を配る。これまでの `msw init`（`public/` に置く）が要らない
- `import.meta.env.DEV` で囲めば、本番のビルドに MSW も偽物のデータも入らなかった
- MSW 3 は、名前が変わったものがある。`onUnhandledRequest` → `onUnhandledFrame`、`graphql` は `msw/graphql` から

### jsdom の単体テストでつまずいたこと

`setupServer`（Node 用の MSW）を、ふつうの書き方（`beforeAll(() => server.listen())`）で動かすと、MSW を素通りして本物の `localhost:3000` に送られ、`ECONNREFUSED` で落ちた。

oRPC のクライアント（`RPCLink`）は、作られたときに `globalThis.fetch` を覚えておく（`this.fetch = options.fetch ?? globalThis.fetch.bind(globalThis)`）。テストのファイルが `orpc.ts` を読んだ時点でクライアントが作られ、そのあとの `beforeAll` で MSW が `fetch` を差し替えても、クライアントは古い `fetch` を使い続ける。

setup のファイルの一番上で `server.listen()` を呼ぶと通った。setup のファイルは、テストのファイルより先に読まれるため。

```ts
// apps/web/src/setup.ts
const server = setupServer(...handlers);
server.listen(); // beforeAll ではなく、読み込んだ時点で
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
```

`RPCLink` の `fetch` オプションに `(...args) => fetch(...args)` を渡して、呼ぶたびに今の `fetch` を探す形にしても直るはず（試していない）。

### API だけを Bun で動かす

| パッケージ | パッケージ管理 | 動かすもの                                                   |
| ---------- | -------------- | ------------------------------------------------------------ |
| `apps/web` | pnpm           | Node.js（Vite の開発サーバー、`vp test`）                    |
| `apps/api` | pnpm           | **Bun**（API のサーバー）。単体テスト（`vp test`）は Node.js |

Vite+ は、Bun を**パッケージ管理**としては扱える（`vp create --package-manager bun`、`vp env` の `bun` の shim）。ただし、`vp env` が管理する**実行環境**は Node.js だけ（Vite+ の docs の env.md: 「one Node.js runtime and one selected package manager」）。そこで、パッケージ管理は pnpm のまま、`apps/api` の Bun だけを pnpm に管理させた。

```jsonc
// apps/api/package.json
"scripts": { "start": "bun src/server.bun.ts" },
"devEngines": {
  "runtime": { "name": "bun", "version": "1.4.3", "onFail": "download" }
}
```

- `vp install` すると、pnpm が Bun 1.4.3 を落とし、lockfile に OS ごとのチェックサム付きで記録した（`bun@runtime:1.4.3`）
- `vp run api#start` も `pnpm --filter api run start` も、pnpm が入れた Bun（`node_modules/.pnpm/bun@runtime+1.4.3/`）で動いた。この PC には mise の Bun もあるが、そちらは使われなかった
- Bun で起動した API を、web と同じ約束の型のクライアントで呼べた。約束にない入力は `Input validation failed` で弾かれた

Bun の API は、起動用のファイル（`server.bun.ts`）だけで使う。中身の `app.ts` は Web 標準の API だけで書く。こうすると、Node.js で動く `vp test` からも `app.ts` を読める（`app.request()` で API を呼ぶテストが通った）。フロントは `packages/contract` しか読まないので、Bun の API がフロントの型チェックに漏れることもない。

```ts
// apps/api/src/server.bun.ts
import { app } from "./app.ts";

export default { port: Number(process.env.PORT ?? 8787), fetch: app.fetch };
```

#### `vp install` 1 回で、3 つともそろう

PC に無い Node.js（24.13.0）を、ルートの `package.json` の `devEngines.runtime` に書いて、`node_modules` の無い状態で `vp install` した。

| もの            | 誰が入れるか                                   | 書く場所                                               |
| --------------- | ---------------------------------------------- | ------------------------------------------------------ |
| Node.js 24.13.0 | Vite+（nodejs.org から落とし、署名も確かめる） | ルートの `package.json` の `devEngines.runtime`        |
| pnpm            | Vite+                                          | ルートの `package.json` の `devEngines.packageManager` |
| Bun 1.4.3       | pnpm                                           | `apps/api/package.json` の `devEngines.runtime`        |

`vp install` のあと、Node.js 24.13.0 が入っていて（`vp env list node`）、Bun も `node_modules/.pnpm/bun@runtime+1.4.3/` に入っていた。クローンした人は `vp install` を 1 回打てば、版のそろった 3 つで動かせる。試したあと、Node.js 24.13.0 は `vp env uninstall 24.13.0` で消した。

#### `runtimeOnFail: ignore` を入れると、pnpm が Bun を入れなくなる

Vite+ の docs は、pnpm の設定に `runtimeOnFail: ignore` を入れるよう勧めている（[docs/18](18-pnpm%20の設定.md)）。コピーしたモノレポで入れてみた。

- lockfile から `bun@runtime` が消え、pnpm は Bun を入れなくなった
- `bun` は、PC に入っている別の Bun（この PC では mise の shim が、Vite+ が前に入れた Bun 1.4.3 を呼んだ）で動いた。**たまたま PC に Bun があったから動いただけ**で、プロジェクトでは版を固定できない。Bun の無い PC では動かない

Bun の API を pnpm に管理させるなら、`runtimeOnFail: ignore` は入れない。このリポジトリでも入れていない。

#### `vp run` は、環境変数をそのまま渡さない

`PORT=8788 vp run api#start` で起動すると、`PORT` が届かず、既定の 8787 で起動した。`vp run` のタスクは、きれいな環境で動く。渡るのは `PATH`・`HOME`・`CI` などの決まったものだけ（Vite+ の docs の cache.md）。渡したい環境変数は、`vite.config.ts` の `run` の `cache.untrackedEnv`（キャッシュには含めない）か `cache.env`（キャッシュにも含める）に書く。

### CSS Modules はワークスペースのパッケージのまま読める

```jsonc
// packages/ui/package.json
"exports": { "./Button": "./src/Button/Button.tsx" }
```

`apps/web` から `import { Button } from "@mono/ui/Button"` で読むと、開発サーバーでもビルドでも、`.module.css` がふつうに処理された（クラス名が `_button_1jsvb_1` のようになり、色が付いた）。pnpm のワークスペースのパッケージは、`node_modules` の中ではなく元のフォルダへのリンクなので、Vite は自分のソースと同じように扱う。

このリポジトリのデザインシステムを `packages/ui` に持っていくときも、ビルドせずにソースのまま渡せそう。

## 新しいリポジトリを作るときのメモ

- `vp create vite:monorepo` は、そのときのグローバルの Node.js と pnpm（今回は Node 24.22.0、pnpm 12.14.0）で `devEngines` を書く。このリポジトリと同じく、具体的なバージョンで固定し直す
- ひな形の `pnpm-workspace.yaml` は `catalogMode: prefer`（`vp add` が catalog に寄せる）。このリポジトリの pnpm の設定（[docs/18](18-pnpm%20の設定.md)）を持っていく
- TypeScript 7 の `tsc` は、`vp run` のキャッシュが変更に気づかない。`tsc` のタスクは `cache: false` にする（[docs/01](01-学習の進め方.md) の「ツールの決まり」）
- TanStack Query（`@tanstack/react-query`）は、今回は入れていない。公開から 1 日の版しかなく、2 日のルール（[docs/18](18-pnpm%20の設定.md)）に引っかかるため。`@orpc/tanstack-query` で、oRPC と組み合わせられる
