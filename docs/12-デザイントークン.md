# デザイントークン

記録日: 2026-10-18

段階 2。色・余白・文字サイズ・角丸・影・重なりの値を、CSS 変数（カスタムプロパティ）にまとめた。部品は値を直接書かず、トークンを使う。

## ファイル

```
src/styles/
├── global.css               トークンを読み込み、body に背景と文字の色を付ける
├── tokens/                  トークンだけを置く
│   ├── primitive/           ← 部品から使わない
│   │   └── color.css        色の材料（青の 900 番、灰色の 536 番など）
│   │
│   ├── color.css            ← ここから下は部品が使う。色（意味のトークン）
│   ├── font.css             書体・文字サイズ・文字の太さ
│   ├── line-height.css      行の高さ
│   ├── border-radius.css    角丸
│   ├── elevation.css        影
│   ├── spacing.css          余白（自分で作った）
│   ├── size.css             部品の大きさ（自分で作った）
│   ├── z-index.css          重なりの順番（自分で作った）
│   └── DADS-LICENSE.txt     DADS を元にしたファイルのライセンス
└── stories/                 Storybook のトークンのページ（下の「Storybook のトークンのページ」）
```

決まりは 1 つ。**`tokens/` の直下の CSS は、部品から使ってよい。`primitive/` の中は使わない。**

`global.css` の先頭で `@import` している。色の材料（`primitive/color.css`）、意味のトークン（`color.css`）の順に並べているのは、読みやすさのため。`var()` は、ブラウザが CSS を読み終えて、要素ごとの値を決めるときに読むので、参照される材料が後にあっても動く。意味のトークンを材料より先に書いた CSS をブラウザで試して、材料の色になることを確かめた。TS で、型の名前を、その定義より前の行で使えるのと似ている。

### この形にした理由

最初は、すべてのトークンを `tokens/` の直下に並べ、色の材料を `color.css`、意味のトークンを `semantic.css` と名付けていた。これだと、部品を書くときに「色はどこ？」と探して最初に開く `color.css` が、使ってはいけない材料のほうになる。間違えて `--color-primitive-blue-900` を使うと、ダークモードで切り替わらない。

そこで、次のように変えた。

- **意味のトークンを `color.css` に**：色を探して最初に開くファイルが、正しいほうになる
- **色の材料を `primitive/` に**：フォルダ名が「材料なので直接使わない」という目印になる

`primitive/` に入れたのは色だけ。余白や文字サイズは、明るくても暗くても同じ値なので、意味の段を挟まずに部品から直接使う。

### ファイル名は、トークンの名前の始まりにそろえる

トークンの名前は `--<ファイル名>-` で始める。`--font-size-16` は `font.css`、`--line-height-150` は `line-height.css` にある。名前を見れば、どのファイルを開けばよいか分かる。TS で、`PAGES` が `constants/pages.ts`、`URLS` が `constants/urls.ts` にあるのと同じ。

最初は、次のトークンで名前とファイルがずれていた。段階 3 の途中（2026-10-18）にそろえた。

| トークン                                             | 前に置いていたファイル | 今のファイル                  |
| ---------------------------------------------------- | ---------------------- | ----------------------------- |
| `--font-weight-*`（文字の太さ）                      | `font-size.css`        | `font.css`                    |
| `--font-family-body`・`--line-height-body`（本文用） | `color.css`            | `font.css`・`line-height.css` |
| `--size-touch-target`（押せる部品の大きさ）          | `spacing.css`          | `size.css`                    |

ずれていたトークンは、探しにくいだけでなく、トークンの一覧のページにも出ていなかった（下の「一覧は CSS ファイルから作る」）。

文字のトークンは、書体（`font-family.css`）と、文字サイズ・太さ（`font-size.css`）の 2 つのファイルに分けていたのを、`font.css` にまとめた。3 つとも名前が `--font-` で始まり、CSS のプロパティも `font-family`・`font-size`・`font-weight` で同じ仲間のため。行の高さは、名前もプロパティも `line-height` なので、`line-height.css` のまま分けている。

### 間違えたら lint で止める

フォルダを分けても、間違えて書けてしまうことは変わらない。そこで [Stylelint](https://stylelint.io/)（CSS の lint）で、部品の CSS に色の値や色の材料を書いたら止める。定義のない CSS 変数（打ち間違い）も止める。

| ルール                                                      | 止めるもの                                                      |
| ----------------------------------------------------------- | --------------------------------------------------------------- |
| `color-no-hex`                                              | `#fff` のような色の値                                           |
| `color-named`                                               | `white` のような色の名前                                        |
| `function-disallowed-list`                                  | `rgb()`・`oklch()` などで色を作ること                           |
| `declaration-property-value-disallowed-list`                | `--color-primitive-*`・`--color-neutral-*`（色の材料）          |
| `csstools/value-no-unknown-custom-properties`（プラグイン） | 定義のない CSS 変数（`var(--color-primay)` のような打ち間違い） |

`color-mix()` は止めない。ボタンにマウスを乗せたときの色のように、意味のトークンどうしを混ぜて作るときに使うため（`color-mix(in oklab, var(--color-primary), var(--color-background) 20%)`。灰色に近い色と混ぜるときは oklab にする。理由は docs/13）。

`tokens/` の中は、色の値や材料を定義する場所なので検査しない（`stylelint.config.js` の `ignoreFiles`）。

違反すると、日本語で直し方が出る。

```
src/components/ui/Card/Card.module.css
  43:10  ✖  色の値を直接書かず、src/styles/tokens/color.css の意味のトークン（--color-primary など）を使ってください（docs/12）  color-no-hex
  46:18  ✖  色の材料（--color-primitive-* など）は使わず、src/styles/tokens/color.css の意味のトークン（--color-primary など）を使ってください（docs/12）  declaration-property-value-disallowed-list
```

| 場面             | 動き                                                                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 書いている最中   | VS Code の Stylelint の拡張機能（`stylelint.vscode-stylelint`）が、違反に赤線を出す。`.vscode/extensions.json` のおすすめに入れている |
| 自分で実行する   | `vp run lint:css`                                                                                                                     |
| コミットするとき | `src/` の CSS をステージしていれば、`vite.config.ts` の `staged` から動く。違反があるとコミットが止まる                               |

- Stylelint の見た目の書き方のルール（`stylelint-config-standard`）は入れていない。整形は Oxfmt（`vp check`）が受け持つので、役割がぶつかるため。CSS Modules のクラス名（`.navList` のような camelCase）も、標準のルールでは弾かれる
- コミット時は、ステージした CSS のファイル名を Stylelint に渡す。`tokens/` だけをステージしたときは、検査するファイルが 0 になってエラーになるので、`--allow-empty-input` を付けている
- Vite+ には CSS の lint がないので、Stylelint を別に入れた。`vp check` には含まれない
- Stylelint の拡張機能（2.2.1、Stylelint 17 に対応）は、プロジェクトに入っている Stylelint と `stylelint.config.js` をそのまま使う。設定は足していない（`.module.css` も CSS として検査される）
- 拡張機能の README は、VS Code の標準の CSS の検査を止めることを勧めている（同じ間違いが 2 回出ないように）。このリポジトリでは止めない。Stylelint に入れているのは独自の決まりだけで、標準の検査（知らないプロパティ名など）とかぶらないため

#### 定義のない CSS 変数を止める

CSS 変数の名前を打ち間違えても、CSS はエラーにならない。`var(--color-primay)` の指定は、なかったことになるだけ（背景なら透明、文字の色なら親の色）。見た目では気づけないこともある。

そこで、Stylelint のプラグイン [`stylelint-value-no-unknown-custom-properties`](https://github.com/csstools/stylelint-value-no-unknown-custom-properties)（csstools 製、6.1.1）を入れた。定義のない名前を `var()` で使うと止める。わざと打ち間違えて試したときの出力。

```
src/components/ui/Button/Probe.module.css
  3:14  ✖  --color-primay は定義されていない CSS 変数です。打ち間違いがないか、src/styles/tokens/ のトークンの名前を確かめてください（docs/12）  csstools/value-no-unknown-custom-properties
```

定義のある名前として扱うのは、次の 2 つ。

| 定義のある名前                               | 例                                                       |
| -------------------------------------------- | -------------------------------------------------------- |
| `global.css` が `@import` で読み込むトークン | `--color-primary`、`--spacing-16`、`--size-touch-target` |
| 同じファイルの中で定義した変数               | Button の `--button-background`（`.primary` の中で定義） |

- トークンは、`stylelint.config.js` の `importFrom` に `global.css` を渡して集めている。プラグインは `@import` をたどるので、アプリと同じ入口から、すべてのトークンが集まる。トークンのファイルを足しても、`global.css` に `@import` を足せば、設定は変えなくてよい
- `importFrom` の相対パスは、Stylelint を実行した場所から探される（README より）。どこから実行しても同じになるよう、`import.meta.dirname` で絶対パスにしている。別のフォルダから実行して、同じ結果になることを確かめた

色の材料（`--color-primitive-*` など）も定義はあるので、このルールでは止めない。止めるのは `declaration-property-value-disallowed-list` で、確かめることを分けている。

| 確かめること     | ルール                                        | TS で言えば                     |
| ---------------- | --------------------------------------------- | ------------------------------- |
| 名前が**ある**か | `csstools/value-no-unknown-custom-properties` | `tsc` の「Cannot find name」    |
| 使って**よい**か | `declaration-property-value-disallowed-list`  | lint の `no-restricted-imports` |

1 つの間違いに、1 つのエラーが出る。色の材料を使うと、「色の材料は使わず…」のエラーだけが出る。

止められないもの。

- 予備の値（フォールバック）付きの `var(--x, 予備の値)`。名前がなくても予備の値が使われるので、プラグインは止めない（ソースで確かめた）
- TSX の `style={{ gap: "var(--spacing-8)" }}`。Stylelint は CSS のファイルしか見ない

#### なぜ Stylelint なのか

Stylelint は CSS 専用の lint で、最初のバージョン（0.1.0）が出たのは 2015 年 7 月。10 年以上続く定番で、ESLint と同じく JavaScript で書かれている。中では PostCSS で CSS を木の形に読み込み、ルールでたどる。

Rust 製の速いものには [Biome](https://biomejs.dev/) がある。lint と整形を 1 つでこなす道具で、[2024 年の v1.9](https://biomejs.dev/blog/biome-v1-9/) で CSS の lint と整形が正式な機能になった（そのときのルールは、Stylelint から移植した 15 個ほど）。Oxc（Oxlint・Oxfmt）には、2026-10 の時点で CSS の lint はない。Lightning CSS も Rust 製だが、変換と圧縮の道具で lint ではない。

|                                      | Stylelint           | Biome（CSS）                                        |
| ------------------------------------ | ------------------- | --------------------------------------------------- |
| 書かれている言語                     | JavaScript          | Rust（速い）                                        |
| ルールの数                           | とても多い          | まだ少ない                                          |
| 今回の「この書き方を禁止する」ルール | すべてある          | あるか確かめられなかった                            |
| 違反の文言を自分で書く               | できる（`message`） | 設定ではできないはず                                |
| 今のツールとの関係                   | lint だけを足せる   | lint と整形がセットで、Oxlint・Oxfmt と役割がかぶる |

このリポジトリでやりたいのは、「色の値や色の材料を書かせない」という独自の決まり。Stylelint なら設定だけで書け、日本語の文言も出せる。Biome を入れると、lint と整形の道具が Oxc と 2 つ並び、どちらの担当か分かりにくくなる。CSS のファイルが数個なら、Stylelint でも一瞬で終わるので、速さの差も気にならない。

段階 4 で Tailwind を入れるときや、CSS が増えて遅くなってきたときに、Biome や Oxc の CSS の対応を見直す。

## 2 段の構造

```
色の材料（primitive/color.css）
  --color-primitive-blue-900: #0017c1;
  --color-neutral-solid-gray-900: #1a1a1a;
        │ 参照する
        ▼
意味のトークン（color.css）
  --color-primary: light-dark(var(--color-primitive-blue-900), var(--color-primitive-blue-400));
        │ 使う
        ▼
部品（Card、Header …）
  color: var(--color-primary);
```

- **基本のトークン**は「どんな色か」を表す。青の 900 番、灰色の 536 番など
- **意味のトークン**は「何に使う色か」を表す。メインの色、背景、枠線など
- **部品は、色については意味のトークンだけを使う。** ブランドの色を変えたいときは `--color-primary` の参照先を書き換えるだけで、全部品に効く。TS で言えば、実装ではなくインターフェースに依存するのと同じ

余白・文字サイズ・角丸・影は、意味の段を作らず、基本のトークン（`--spacing-24`・`--font-size-20` など）を部品から直接使う。ダークモードで変わらないので、間に段を挟む理由がないため。

### primitive という名前

`primitive/` は、TS の「プリミティブ型」と同じ言葉。`string`・`number` のような、それ以上分けられない基本の型のこと。

TS では、基本の型に意味の名前を付けた型を作って使う。

```ts
type Email = string; // 「何に使う文字列か」を名前にする
```

`Email` を作らずに、あちこちで `string` のまま使い回すのは「Primitive Obsession（基本の型へのこだわり）」と呼ばれ、リファクタリングで直す対象になる。トークンも同じ関係になっている。

| TS                                | トークン                                   | 置き場所                     |
| --------------------------------- | ------------------------------------------ | ---------------------------- |
| `string`（基本の型）              | `--color-primitive-blue-900`（どんな色か） | `tokens/primitive/color.css` |
| `type Email = string`（意味の型） | `--color-primary`（何に使う色か）          | `tokens/color.css`           |
| 部品の中だけの型                  | `--button-background`                      | `Button.module.css`          |

部品が `--color-primitive-blue-900` を直接使うのは、`Email` を使わずに `string` を使うのと同じ。

デザイントークンの世界でも、この 3 段を primitive → semantic → component と呼ぶのが普通。GitHub のデザインシステム（Primer）は、トークンのパッケージ名が `@primer/primitives`。元にした DADS のトークン名も `--color-primitive-*`。

2026-10-18 に、フォルダ名を `palette/` に変える案や、`tokens/` の外に出す案も考えたが、共通の言葉なので `primitive` のままにした。

- `palette/` は中身が分かりやすいが、トークン名の `primitive` とずれる。Tailwind ではパレットの色（`bg-blue-500`）を部品から直接使うので、「直接使ってよい」とも読める
- `tokens/` の外に出すと「`tokens/` の中は全部使ってよい」と決まりは単純になるが、材料もデザイントークンなのに外にあるのは不自然

## 値はデジタル庁デザインシステムを元にした

色・文字・行の高さ・角丸・影の値は、[デジタル庁デザインシステム](https://design.digital.go.jp/)（DADS）のデザイントークン（[`@digital-go-jp/design-tokens`](https://www.npmjs.com/package/@digital-go-jp/design-tokens) 2.0.1）を元にしている。

- MIT ライセンスなので、著作権表示とライセンス文を `tokens/DADS-LICENSE.txt` に残している。MIT は「使ってよいが、著作権表示とライセンス文を含めること」が条件。元にした 5 つのファイルの先頭にも、出どころとこのファイルへの参照を書いている
- npm のパッケージは入れず、値を CSS に書き写した。仕組みを学ぶため、自分のファイルとして持つ
- DADS の「ブランドの色」の段（`--color-key-*`）は除いた。その役目は、意味のトークンの `--color-primary` が持つ。両方あると、同じ役目の段が 2 つ並ぶため
- DADS の「状態の色」の段（`--color-semantic-success-2` など）も、段階 3 の途中（2026-10-18）に除いた。成功・エラー・警告という意味は、意味のトークンの `--color-success` などが持つ。材料の中に意味の名前があると、材料と意味のトークンのどちらを使うのか分かりにくくなるため。`--color-success` などは材料の色（緑 800 など）を直接指すようにした。明るい配色の色は、DADS の状態の色と同じまま

### DADS から学んだこと

**灰色の 420 と 536 は、コントラストの境目。** 灰色は 50・100・200…と 100 刻みなのに、この 2 つだけ半端な番号になっている。白い背景とのコントラストを計算すると理由が分かる。

| トークン                         | 色        | 白とのコントラスト | 意味                                                                  |
| -------------------------------- | --------- | ------------------ | --------------------------------------------------------------------- |
| `--color-neutral-solid-gray-420` | `#949494` | 3.03 : 1           | 枠線やアイコン（文字以外）に WCAG が求める 3 : 1 を満たす一番薄い灰色 |
| `--color-neutral-solid-gray-536` | `#767676` | 4.54 : 1           | 普通の文字に WCAG が求める 4.5 : 1 を満たす一番薄い灰色               |

「この番号より濃ければ基準を満たす」という境目を、トークンとして用意している。

**名前に値を入れる。** `--font-size-16: 1rem`、`--border-radius-8: 0.5rem` のように、名前を見れば値が分かる。このリポジトリの余白（`--spacing-24: 1.5rem`）も同じ付け方にした。値を変えると名前とずれるのが弱点なので、値は変えずに、別の名前のトークンを足す。

## 意味のトークン

名前は shadcn/ui に寄せた。段階 4 で shadcn/ui と比べるときに、同じ部品を作り直しやすくするため。

| トークン                                    | 使う場所                         | 明るい配色               | 暗い配色                   |
| ------------------------------------------- | -------------------------------- | ------------------------ | -------------------------- |
| `--color-background`・`--color-foreground`  | ページ全体の背景と文字           | 白 / 灰 900（17.4:1）    | 灰 900 / 白（17.4:1）      |
| `--color-card`・`--color-card-foreground`   | Card などの面                    | 白                       | 灰 800                     |
| `--color-muted`・`--color-muted-foreground` | 控えめな面と、補足の文字         | 灰 50 / 灰 700（8.45:1） | 灰 800 / 灰 300（8.3:1）   |
| `--color-primary`・`-foreground`            | 主なボタン、リンク               | 青 900 / 白（11.1:1）    | 青 400 / 灰 900（6.14:1）  |
| `--color-secondary`・`-foreground`          | 控えめなボタン、選ばれている状態 | 青 50 / 青 900（9.75:1） | 青 1100 / 青 100（13.5:1） |
| `--color-border`                            | 飾りの枠線                       | 灰 200                   | 灰 700                     |
| `--color-ring`                              | フォーカスの輪                   | `--color-primary` と同じ |                            |
| `--color-success`・`error`・`warning`       | 状態の文字                       | 緑 800・赤 800・橙 800   | 緑 400・赤 400・黄 400     |

`-foreground` は「その色の上に載せる文字の色」。背景と文字を組で決めておけば、コントラストも組で確かめられる。表の比は、組の背景（状態の色は `--color-background`）に対する値で、どれも 4.5 : 1 以上。

`--color-border` は飾りの線なので 3 : 1 に届かない。入力欄の枠のように、形を見せるための線には 3 : 1 以上の色（灰 420 より濃い色）を使う。段階 3 で Input を作るときに足す。

## ダークモード

```css
:root {
  color-scheme: light dark;
  --color-background: light-dark(var(--color-neutral-white), var(--color-neutral-solid-gray-900));
}
```

- `color-scheme: light dark` で、「このページは明るい配色と暗い配色の両方に対応している」とブラウザに伝える。OS やブラウザの設定に合わせて、どちらかが選ばれる。ボタンやスクロールバーなど、ブラウザが描く部分も暗くなる
- `light-dark(明るいときの値, 暗いときの値)` は、選ばれた配色に合わせて、どちらかの値になる
- **基本のトークンは、明るくても暗くても同じ値。** 変わるのは、意味のトークンが「どれを指すか」だけ。2 段の構造にしておくと、ダークモードは意味のトークンを書き換えるだけで済む

`prefers-color-scheme` のメディアクエリで 2 回書く方法もあるが、`light-dark()` なら 1 行に明るいときと暗いときが並ぶので、組で見比べやすい。

### 試し方

macOS なら「システム設定 → 外観」をダークにする。または、Chrome の開発者ツールの「レンダリング」タブで `prefers-color-scheme: dark` を選ぶ。

## 余白・大きさ・重なりは自分で作った

DADS のパッケージには、余白・大きさ・z-index のトークンがない。

**余白**（`spacing.css`）は、4px を基本の単位にして、小さい余白は細かく、大きい余白は粗く刻んだ。名前は DADS と同じく px の値にした。

```css
--spacing-4: 0.25rem;
--spacing-8: 0.5rem;
--spacing-12: 0.75rem;
--spacing-16: 1rem;
--spacing-24: 1.5rem;
```

**大きさ**（`size.css`）は、部品そのものの大きさ（`width`・`height`・`min-width`・`min-height`）のトークン。今は、押せる部品の最小の大きさだけがある。

```css
--size-touch-target: max(2.75rem, 44px); /* 44px */
```

- 名前は、下の重なりと同じく**何に使うかの名前**にした。`--size-44` と書かれても、何のための 44px か分からないため
- 値を `max()` にしたのは、44px を下回らないようにするため。`2.75rem` だけだと、ブラウザの文字サイズを初期設定（16px）より小さくしている人では、44px より小さくなる（14px なら 38.5px）。WCAG の 2.5.5（いちばん厳しい AAA の基準）も「44 × 44 CSS ピクセル以上」で、px で決まっている。`max()` なら、文字を大きくしている人には一緒に大きくなる

最初は `spacing.css` に置いていたが、段階 3 で Button を作ったときに `size.css` に分けた（2026-10-18）。

- 役割が違う。余白は部品と部品の**間**の長さで、こちらは部品**そのもの**の大きさ。どちらも長さだが、`src/constants/` で `pages.ts` と `urls.ts` を分けたのと同じく、役割で分けた
- 見つけられなかった。`spacing.css` に置いていた間は、トークンの一覧のページにも、`src/styles/README.md` の表にも出ていなかった（下の「一覧は CSS ファイルから作る」）

**重なり**（`z-index.css`）も、値ではなく**使う場所の名前**にした。`--z-index-100` と書かれても、何の重なりか分からないため。

```css
--z-index-dropdown: 100;
--z-index-header: 200;
--z-index-modal: 300;
--z-index-toast: 400;
```

## 部品で直接書いてよい値

レイアウトの境目は、部品ごとの値なのでトークンにしない。

- CardList の `minmax(min(16rem, 100%), 1fr)` の `16rem`（1 列の最小の幅）
- Header の `@container header (width < 30rem)` の `30rem`（余白を詰める境目）
- 枠線の太さの `1px`

## VS Code で定義に飛ぶ

部品の CSS の `var(--color-primary)` から `tokens/color.css` の定義へは、VS Code の標準の機能では飛べない。

### 飛べない理由

VS Code の CSS の機能（`vscode-css-languageservice` 6.3.10）は、今開いているファイルの中しか探さない。定義を探す関数を読んで確かめた。

```js
findDefinition(document, position, stylesheet) {
  const symbols = new Symbols(stylesheet); // 今のファイルの中身だけから探す
  // ...
  return { uri: document.uri, range: /* ... */ }; // 返す場所は、いつも今のファイル
}
```

同じファイルで定義した `--button-background` には飛べるが、別のファイルのトークンには飛べない。

TS で定義に飛べるのは、`import` が定義のあるファイルを教えてくれるから。CSS 変数には `import` がない。部品の CSS はトークンを import せず、`global.css` が `:root` に入れた値を、どの要素も親から受け継ぐ。どの値になるかは、画面を表示するときに、要素の親をたどって決まる。React の Context に近い。

| CSS 変数                                | React の Context                    |
| --------------------------------------- | ----------------------------------- |
| `:root { --color-primary: ... }`        | アプリの一番外の `<Provider value>` |
| `.primary { --button-background: ... }` | 途中で値を上書きする `<Provider>`   |
| `var(--button-background)`              | `useContext()`                      |

`useContext()` を書いた場所だけでは、どの Provider の値になるか決められない。CSS 変数も同じなので、標準の機能は、確実に分かる同じファイルの中だけを探す。

### 拡張機能で飛べるようにする

プロジェクトの CSS を読んで、変数の名前と定義の場所の一覧を作る拡張機能を使う。2026-10-18 に、VS Code Marketplace と GitHub で 3 つを比べた。

| 拡張機能                                                             | インストール数 | 最後の更新 | 状態                                     |
| -------------------------------------------------------------------- | -------------- | ---------- | ---------------------------------------- |
| CSS Custom Properties                                                | 約 49 万       | 2021-06    | 5 年以上更新がない                       |
| **CSS Variable Autocomplete**（`vunguyentuan.vscode-css-variables`） | 約 21 万       | 2025-12    | 更新が続いている（MIT）                  |
| CSS Var Complete                                                     | 約 12 万       | 2025-01    | リポジトリがアーカイブされた（開発終了） |

CSS Variable Autocomplete を選んだ。README によると、できることは 2 つ。

- **定義に飛ぶ**：Cmd を押しながらクリックする
- **候補を出す**：`var(--` まで打つと、トークンの一覧が出る。色のトークンには色見本が付く。TSX も対象に入っている

`.vscode/extensions.json` のおすすめに入れたので、このリポジトリを開くと、VS Code が入れるかどうかを聞いてくる。

`.vscode/settings.json` で、読むファイルを `tokens/` の直下だけにした。

```json
"cssVariables.lookupFiles": ["src/styles/tokens/*.css"]
```

- 何も設定しないと、すべての CSS を読む。部品から使ってはいけない `--color-primitive-*` や、Button の中だけの `--button-*` まで候補に出る
- 直下だけにすると、候補に出るのは部品から使ってよいトークンだけになる。部品が使ってよいトークンの決まりと、エディタの候補がそろう
- 代わりに、`color.css` から `primitive/` の定義へは飛べない。トークンそのものを直すときだけなので、検索で足りる
- Stylelint の「定義のある名前」（`global.css` から集める）には、色の材料も入る。エディタの候補は「使ってよいもの」、Stylelint は「あるもの」なので、範囲が違う

## Storybook のトークンのページ

Storybook のサイドバーの **Design Tokens** に、トークンのファイルごとのページがある（`src/styles/stories/`）。ページとトークンのファイルは 1 対 1 で、ページの名前はファイル名にそろえている。

| -------------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Color                | `color.css`           | 色の面。`-foreground` の組があれば、その色で「Aa」を重ねる                                                        |
| Font                 | `font.css`            | 書体は名前と値だけ。文字サイズ・太さは、その大きさ・太さの文字                                                    |
| Line Height          | `line-height.css`     | 2 行に折り返した文章                                                                                              |
| Border Radius        | `border-radius.css`   | トークンを当てた四角                                                                                              |
| Elevation            | `elevation.css`       | トークンを当てた四角                                                                                              |
| Spacing              | `spacing.css`         | トークンの長さの棒                                                                                                |
| Size                 | `size.css`            | トークンの大きさの正方形                                                                                          |
| Z Index              | `z-index.css`         | 名前と値だけ                                                                                                      |
| Primitive / Color    | `primitive/color.css` | 10 色の 13 段階と、白と黒・灰色・透明度のある灰色を、ファイルと同じ順に並べる。部品からは使わないことも書いている |

### サイドバーの分け方と並び順

- 大きな分類（**DESIGN TOKENS**）は、`<Meta title="Design Tokens/Color" />` の `/` の前で決まる。大文字で出るのは、サイドバーの CSS（`text-transform: uppercase`）が大文字にして見せているため。書いた文字は `Design Tokens` のまま
- `/` を 2 つにすると（`Design Tokens/Primitive/Color`）、間の `Primitive` がフォルダになる。`tokens/primitive/` と同じ形にした
- 並び順は `.storybook/preview.tsx` の `storySort` で決めている。何も決めないと、Storybook がファイルを読み込んだ順に並ぶ。`global.css` で読み込む順にそろえ、部品から使わない材料（Primitive）を最後にした

最初は 1 つのページ（Foundations/Tokens）に、すべての節を並べていた。段階 3 の途中（2026-10-18）に、トークンのファイルごとのページに分けた。「Foundations」は段階 2 で付けた名前で、Storybook が決めた名前ではないので、トークンのページだと分かる Design Tokens に変えた。

### ページの置き場所

ページは `src/styles/stories/` に置いている。`tokens/` の隣で、`tokens/` の中にはトークンだけを置く。

一度は `tokens/stories/` に置いたが、段階 3 の途中（2026-10-18）に今の場所へ移した。トークンの名前とファイル名をそろえる決まり（上の「ファイル名は、トークンの名前の始まりにそろえる」）を作ったので、トークンでないファイルは `tokens/` の外に出した。Stylelint で検査しない範囲も `src/styles/tokens/**` の 1 つで書けるようになった。

置き場所は、Storybook の docs（v10）のすすめ方に合わせて決めている。

- 部品のストーリーは、部品と同じフォルダに置く（`ui/Button/Button.stories.tsx`）。ストーリーは開発のときだけ使うファイルで、完成品には入らない
- 部品に結びつかない MDX のページは、サイドバーの場所を `<Meta title="Design Tokens/Color" />` で決める。ファイルの場所はサイドバーに関係しないので、探しやすい場所に置けばよい

紹介のページのように、styles と関係ないページが増えたら、Storybook だけのページの置き場（`src/stories/` など）を作ることを考える。

### 見本を描く部品（`blocks/`）

ページ（`.mdx`）は「import して並べるだけ」にして、見本を描く部品を `src/styles/stories/blocks/` に置いている。

| ファイル            | 役目                                                                                                | 使うページ        |
| ------------------- | --------------------------------------------------------------------------------------------------- | ----------------- |
| `ColorTokens.tsx`   | 色の面を並べ、`-foreground` の組があれば「Aa」を重ねる                                              | Color             |
| `PaletteTokens.tsx` | 1 色の段階を、小さな面で 1 行に並べる。`exclude` で外す名前を指定できる（白と黒の欄で、灰色を外す） | Primitive / Color |
| `ScaleTokens.tsx`   | 1 行に「名前・値・見本」を並べる。見本の描き方は `kind` で選ぶ                                      | 残りの 7 ページ   |
| `panel.module.css`  | 一覧を囲む、今の配色の面（下の「見本は今の配色の面の上に描く」）                                    | 上の 3 つが使う   |

部品が使う関数は、`blocks/` の隣の `src/styles/stories/utils/` に置いている。

| ファイル         | 役目                               | 使うところ          |
| ---------------- | ---------------------------------- | ------------------- |
| `parseTokens.ts` | CSS の文字列からトークンを取り出す | `blocks/` の 3 部品 |

- 部品ごとに 1 つのファイルにし、CSS も部品ごとに分けた（`ui/` の `Card.tsx` と `Card.module.css` と同じ形）。最初は 3 つの部品を `Tokens.tsx` 1 つにまとめていた
- `blocks/` には部品だけを置き、関数は `utils/` に分けた。React でよくある `components/` と `utils/` の分け方と同じ。`src/utils/` に置かないのは、Storybook のトークンのページでしか使わず、アプリの関数に見えてしまうため
- ページごとには分けなかった。7 ページは同じ表を出していて、違うのは見本の描き方だけなので、ページごとに作ると同じ表を 7 回包むことになる
- フォルダ名の `blocks` は、Storybook の呼び方から取った。MDX のページに置く部品を Doc Blocks と呼ぶ（`import { Meta } from "@storybook/addon-docs/blocks"` の `blocks`）。`components` にすると、アプリの部品の `src/components/` とまぎらわしい
- 分ける前と後で、9 ページを明るい配色と暗い配色でスクリーンショットに撮って比べた。18 枚とも同じだった

### `.mdx` とは

トークンのページは `.mdx`（`color.mdx` など）で書いている。**MDX は Markdown + JSX** で、Markdown の中に `import` と React の部品を書ける形式。

|            | 素の形式 | JSX を足した形式 |
| ---------- | -------- | ---------------- |
| TypeScript | `.ts`    | `.tsx`           |
| Markdown   | `.md`    | `.mdx`           |

`.tsx` が「TS の中に `<div>` を書ける」ように、`.mdx` は「Markdown の中に `<ColorTokens />` を書ける」。

```mdx
{/* src/styles/stories/spacing.mdx */}
import { Meta } from "@storybook/addon-docs/blocks";

import spacingCss from "~/styles/tokens/spacing.css?raw";

import { ScaleTokens } from "~/styles/stories/blocks/ScaleTokens";

<Meta title="Design Tokens/Spacing" />

# 余白

`src/styles/tokens/spacing.css` のトークン。gap・margin・padding は、ここの値から選ぶ。

<ScaleTokens css={spacingCss} prefix="--spacing-" kind="spacing" />
```

見出しや文章は Markdown で書き、動きが必要な見本だけ React の部品を差し込む。

|                    | `.md`                             | `.mdx`                                                                        |
| ------------------ | --------------------------------- | ----------------------------------------------------------------------------- |
| 書けるもの         | 文章・表・コード例                | それに加えて、`import` と React の部品                                        |
| 中身の扱い         | HTML に変換されるだけ             | JS のモジュールにコンパイルされる（ファイル全体が 1 つの React の部品になる） |
| 読むのに必要なもの | GitHub やエディタでそのまま読める | Storybook のような、MDX をコンパイルできる道具                                |
| 使われている場所   | README、このリポジトリの `docs/`  | Storybook の docs、ドキュメントのサイト（Docusaurus など）                    |

`docs/` は `.md` のままにしている。GitHub やエディタで、何もしなくても読めるため。動く見本が要る Storybook のページだけ `.mdx` にした。

#### 気をつけること

**`{` と `<` が特別な意味を持つ。** `{ ... }` は JS の式として実行され、`<` は部品の始まりとして読まれる。文章の中に `{` や `<div>` をそのまま書くと壊れることがあるので、コードはバッククォートで囲む。HTML のコメント（`<!-- -->`）も使えないので、`{/* */}` で書く。

**型チェックと lint の目が届かない。** このリポジトリで確かめた結果。

| 道具               | `.mdx` を見るか                                    |
| ------------------ | -------------------------------------------------- |
| Oxfmt（整形）      | 見る                                               |
| 型チェック（tsc）  | 見ない                                             |
| Oxlint             | 見ない                                             |
| dependency-cruiser | 見ない（検査したファイルに `.mdx` が入っていない） |

ページ（`.mdx`）の import を書き間違えても、`vp check` は通ってしまう。間違いに気づくのは、Storybook でページを開いたとき。そのため、ロジックは型チェックと lint が効く `blocks/` の部品（`.tsx`）に寄せ、ページには「import して並べるだけ」を書く。ページを変えたら、Storybook で開いて確かめる。

ページから部品を読むときは、`~/styles/stories/blocks/ScaleTokens` のように `~/` から書く（`./` で書くのは同じフォルダのファイルだけ、という決まりのため）。

### 一覧は CSS ファイルから作る

トークンの名前と値は、ページに手で書かず、CSS ファイルから取り出している。

```mdx
import spacingCss from "~/styles/tokens/spacing.css?raw";

<ScaleTokens css={spacingCss} prefix="--spacing-" kind="spacing" />
```

- `?raw` を付けて import すると、Vite は CSS をスタイルとして読み込まず、ファイルの中身を文字列として渡す
- `utils/parseTokens.ts` が、その文字列から `--名前: 値;` を正規表現で取り出し、`blocks/` の部品が並べる
- トークンを足したり値を変えたりしても、ページを書き直さなくてよい。一覧と CSS がずれない
- 一覧に出すトークンは、名前の始まり（`prefix`）で選んでいる。ファイルの中に、違う始まりのトークンを置くと出てこない。`--size-touch-target` を `spacing.css` に置いていた間は、余白の欄（`--spacing-` で始まるものだけ）に出ていなかった。`color.css` に置いていた `--font-family-body` と `--line-height-body` も同じだった。上の「ファイル名は、トークンの名前の始まりにそろえる」を守れば、この落とし穴には入らない。材料のページも、欄が 7 つしかなく、シアン・ライム・マゼンタ・紫と、白と黒、透明度のある灰色の 66 個が出ていなかった（2026-10-18 に、ファイルと同じ順で全部の欄を足した）。ページに欄を足すときは、ファイルの中のトークンと数が合うかを確かめる。新しい種類のトークンは、ファイルを分けて、ページを足す（`storySort` の並び順にも足す）

### 見本は「今の配色の面」の上に描く

Storybook の docs のページは、OS の配色に関係なく背景が白い。トークンは暗い配色に切り替わるので、そのまま描くと、白い背景に暗い色の見本が載って、組み合わせが正しく見えない（暗い配色で、行の高さの見本の文字が読めなくなった）。

そこで、一覧ごとに `--color-background` と `--color-foreground` を付けた面（`blocks/panel.module.css` の `.panel`）で囲んでいる。OS の外観をダークにすると、面ごと暗い配色になる。

最初は「名前・値・見本」を `<table>` で並べたが、Storybook の docs が表に付ける縞模様の色のほうが優先され、暗い配色で行が白黒の縞になった。表をやめて、CSS Grid の `subgrid` で並べている。

### 気づいたこと: 暗い配色では影がほとんど見えない

暗い背景の上では、黒い影はほとんど見えない。DADS の影のトークンは明るい配色だけを前提にしている。暗い配色では、影の代わりに枠線や面の明るさの差で浮き上がりを表すことが多い。部品で影を使うときに考える。
