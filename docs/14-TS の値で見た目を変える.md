# TS の値で見た目を変える

記録日: 2026-10-18

CSS Modules で、TS 側の値（状態や数）によって見た目を変える方法。幅を変える、重なりを変える、のように「ロジックで UI が変わる」ときの書き方。

## 判断の順番

1. **ブラウザがもう知っている状態か** → CSS だけで書く。TS は要らない
2. **アプリだけが知っている状態か** → data 属性で伝える（部品の種類はクラス）
3. **連続した値か** → CSS 変数で伝える

| TS 側の値                | TS の型で言うと                          | CSS への渡し方                             | このリポジトリの例                                             |
| ------------------------ | ---------------------------------------- | ------------------------------------------ | -------------------------------------------------------------- |
| ブラウザが知っている状態 | （TS では持たない）                      | 疑似クラス・メディアクエリ・コンテナクエリ | Button の `:hover`・`:focus-visible`、ヘッダーのコンテナクエリ |
| アプリの状態             | ユニオン型（`"open" \| "closed"`）       | data 属性・ARIA 属性                       | Button の `[data-disabled]`、ヘッダーの `[aria-current]`       |
| 部品の種類               | ユニオン型（`"primary" \| "secondary"`） | クラスの切り替え                           | Button の `styles[variant]`                                    |
| 連続した値               | `number`                                 | CSS 変数（`style` で渡す）                 | まだない（Base UI の `--available-height` など）               |

TS は「今どの状態か・いくつか」だけを渡し、「どう見せるか」は CSS が決める。React で、部品が props を受け取って描き方を決めるのと同じ分担。

Base UI の docs（`node_modules/@base-ui/react/docs/react/handbook/styling.md` の「Style hooks」）も、クラス・data 属性・CSS 変数・`style` を同じように使い分けている。

## 1. ブラウザが知っている状態は CSS だけで書く

マウスが乗っている（`:hover`）、キーボードで選ばれた（`:focus-visible`）、チェックされた（`:checked`）、無効（`:disabled`）、置き場所の幅（コンテナクエリ）、OS の設定（`prefers-color-scheme`・`prefers-reduced-motion`）は、ブラウザがもう知っている。

これらを TS で追いかけない。`mouseenter` で「乗っている」を state に持ったり、要素の幅を TS で測って切り替えたりすると、CSS で 1 行のことにロジックが増える。

```css
/* ヘッダーの幅が狭いときは、余白を詰める（docs/10） */
@container header (width < 30rem) {
  .inner {
    column-gap: var(--spacing-12);
  }
}
```

## 2. アプリの状態は data 属性で伝える

開いている・選ばれている・送信中のように、アプリだけが知っている状態は、data 属性で要素に書き出し、CSS は属性で見分ける。

```tsx
<div className={styles.panel} data-state={isOpen ? "open" : "closed"}>
```

```css
.panel[data-state="open"] {
  border-color: var(--color-primary);
}
```

Base UI の部品は、状態の data 属性を自分で付ける（Button の無効は `data-disabled`、Switch のオンは `data-checked` など）。自分で作る部品も同じ形にそろえると、CSS の書き方が 1 つで済む。開発者ツールで、今どの状態かも見える。

### ARIA の属性があれば、それを使う

状態を表す ARIA の属性（`aria-expanded`・`aria-selected`・`aria-current` など）があるなら、data 属性を作らずに、それで見た目を変える。スクリーンリーダーに伝わる状態と、見た目がずれなくなる。ヘッダーの今のページは、TanStack Router が付ける `aria-current="page"` で見た目を変えている（docs/10）。

### 落とし穴: false も属性として残る

React は、data 属性の `true`・`false` を文字にして書き出す。`react-dom/server` で描いて確かめた。

```text
data-open={true}       → <div data-open="true">
data-open={false}      → <div data-open="false">   ← 属性は残る
data-open={undefined}  → <div>
```

CSS の `[data-open]` は「属性があるか」で当たるので、`false` のときにも当たってしまう。次のどちらかで書く。

```tsx
data-open={isOpen || undefined}         // false のときは undefined にして、属性ごと消す
data-state={isOpen ? "open" : "closed"} // 値で分けて、CSS は [data-state="open"] で見る
```

## 3. 部品の種類はクラスで切り替える

primary と secondary のような部品の種類は、クラスを切り替える。Button がこの形。

```tsx
<BaseButton className={`${styles.button} ${styles[variant]}`} />
```

このリポジトリでは「種類はクラス、状態は data 属性」と分けている（`.claude/rules/components.md`）。種類は作るときに決まって変わらないもの、状態は使っている間に変わるもの。

## 4. 連続した値は CSS 変数で渡す

進み具合の 40%、計算した位置のような連続した値は、`style` で CSS 変数に入れ、CSS の側で使う。

```tsx
<div className={styles.bar} style={{ "--progress": `${percent}%` }} />
```

```css
.bar {
  width: var(--progress);
  transition: width 150ms;
}
```

`style={{ width: ... }}` と直接書かずに CSS 変数を挟むのは、CSS 側に仕事を残すため。

- `calc()`・`clamp()`・メディアクエリ・トークンとの組み合わせは、CSS の側で書ける（`width: clamp(var(--spacing-16), var(--progress), 100%)` など）
- Stylelint が検査するのは CSS のファイルだけ。TSX の `style` の中は検査されない（docs/12）

Base UI も同じやり方をしている。Popover は、箱の要素に `--anchor-width`（ボタンの幅）や `--available-height`（画面に収まる高さ）を自分で付けるので、CSS は `max-height: var(--available-height)` と書くだけでよい。

### TS の型

`@types/react` の `CSSProperties` は、`--` で始まる名前を知らない。このリポジトリの TypeScript（7.0）と `@types/react`（19.3.0）で試すと、そのままではエラーになった。

```text
error TS2353: Object literal may only specify known properties,
and '"--progress"' does not exist in type 'Properties<string | number, string & {}>'.
```

直し方は 2 つ。どちらも型チェックが通ることを確かめた。

```tsx
// その場で型を合わせる
style={{ "--progress": `${percent}%` } as CSSProperties}
```

```ts
// 型を 1 回だけ広げる（.d.ts に書く）。何か所も使うなら、こちらのほうが毎回 as を書かなくて済む
declare module "react" {
  interface CSSProperties {
    [key: `--${string}`]: string | number | undefined;
  }
}
```

## z-index を変えたいとき

TS で重なりの数字を計算しない。重なりの順番はデザインの決まりなので、トークン（`--z-index-dropdown`・`--z-index-modal` など）の層から選ぶ（docs/12）。状態で層を変えたいときも、data 属性で切り替えて、CSS がトークンを選ぶ。

「最後に開いたものを上に」のような順番は、Base UI が片付ける。ポップアップを Portal で `<body>` の最後に移すので、後から開いたものほど上に来る。Base UI の docs は、アプリの一番外の要素に `isolation: isolate` を付けることをすすめている。アプリの中の `z-index` が、ポップアップの重なりに割り込まなくなるため。確認ダイアログを作るときに、実物で確かめる。

## Tailwind では（段階 4 で比べる）

考え方は同じ。Base UI の docs の Tailwind の例にも、data 属性で切り替える書き方（`data-starting-style:opacity-0`）と、CSS 変数を使う書き方（`origin-(--transform-origin)`）が出てくる。
