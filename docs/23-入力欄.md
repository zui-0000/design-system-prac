# 入力欄

記録日: 2026-11-05 / 対象: Base UI 1.9.0（`@base-ui/react`）、Storybook 10.6.2

段階 3 の 6 つ目の部品で、段階 4 の `:has()` を一緒に学んだ。作ったのは 3 つのフォルダ。

| 部品                                                                  | 役目                                                           | 元にした Base UI |
| --------------------------------------------------------------------- | -------------------------------------------------------------- | ---------------- |
| `ui/Input`（`Input`・`Textarea`）                                     | 文字を打つ欄。枠の中にアイコンやボタンを置ける                 | `Input`          |
| `ui/Field`（`Field`・`FieldLabel`・`FieldDescription`・`FieldError`） | ラベル・説明・エラーを入力欄に結び付ける                       | `Field`          |
| `ui/Form`（`Form`・`FormActions`）                                    | 送信のときに全部の欄を検証し、最初の失敗した欄へフォーカスする | `Form`           |

```tsx
<Form onFormSubmit={(values) => save(values)}>
  <Field name="email">
    <FieldLabel>メールアドレス</FieldLabel>
    <FieldDescription>返信の宛先に使います。</FieldDescription>
    <Input type="email" required autoComplete="email" />
    <FieldError match="valueMissing">メールアドレスを入力してください。</FieldError>
    <FieldError match="typeMismatch">メールアドレスの形で入力してください。</FieldError>
  </Field>
  <FormActions>
    <Button type="submit" variant="primary">
      送信する
    </Button>
  </FormActions>
</Form>
```

`Textarea` が `ui/Input` にあるのは、枠の CSS が全部同じだから。別のフォルダにすると、枠の CSS を書き写すか、片方からもう片方の CSS を読むことになる。

## `:has()` は、親が中を見るセレクタ

CSS のセレクタは、ふつう親から子へ、前から後ろへしか進めない。`:has()` は、その逆を書ける。

```css
/* 中に .control[data-invalid] を持っている .frame */
.frame:has(.control[data-invalid]) {
  border-color: var(--color-error);
}
```

TS で書けば、`frames.filter((frame) => frame.querySelector(".control[data-invalid]"))`。選ばれるのは中の要素ではなく `.frame` のほう。主要なブラウザには 2023 年 12 月にそろった。

このリポジトリでは 3 か所で使った。どれも「状態を持つ要素と、見た目を変えたい要素が別」という場面。

### 1. 枠の見た目（`Input.module.css`）

本物の `<input>` は枠の中にあり、枠線と輪は親の `.frame` が描く。アイコンやボタンを同じ枠の中に置くため。

```text
┌ .frame（枠線と輪）──────────────────┐
│ 🔍  <input class="control">     [👁] │
└──────────────────────────────────────┘
```

`.frame` はただの `<div>` で、Base UI は `data-*` を付けない。状態が付くのは中の `<input>` だけ。

| 変えたいとき       | 書いたセレクタ                        |
| ------------------ | ------------------------------------- |
| フォーカスしている | `.frame:has(.control:focus-visible)`  |
| 検証で失敗した     | `.frame:has(.control[data-invalid])`  |
| 無効               | `.frame:has(.control[data-disabled])` |

**他の書き方と比べて**

| 書き方                                         | 困ること                                                                                  |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `.frame:focus-within`                          | 右端のボタンにフォーカスしたときも枠に輪が出て、ボタンの輪と 2 重になる                   |
| `.field[data-invalid] .frame`                  | `Field` の中でしか効かない。`Field` なしで置いた `Input`（検索欄など）では動かない        |
| `<input>` の `:invalid`                        | 打つ前の空の `required` の欄も、最初から赤くなる。`validate` やサーバーのエラーも拾えない |
| TSX で状態を受け取り、`.frame` に class を足す | Base UI が持っている状態を、自分でも持ち直すことになる                                    |

Base UI は `Field` の外側（`Field.Root`）にも `data-invalid` を付けるので、`:has()` が唯一の方法というわけではない。`Input` を `Field` なしでも使えるようにしたので、`:has()` を選んだ。

### 2. アイコンの分の余白（`Input.module.css`）

```css
.frame:has(> .icon) .control {
  padding-inline-start: calc(var(--spacing-12) + var(--size-icon) + var(--spacing-8));
}
```

TSX で `icon ? styles.withIcon : ""` と書いてもよいが、「アイコンがあるか」は DOM を見れば分かるので、CSS だけで済ませた。Base UI の docs の例（`forms.md` の Combobox）も、同じ形で `:has` を使っている。

### 3. 「必須」の印（`Field.module.css`）

```css
.field:has(:required) .required {
  display: inline;
}
```

ここが一番 `:has()` らしい使い方。

- Base UI は `Field` に `data-required` を付けない（付くのは `disabled`・`valid`・`invalid`・`dirty`・`touched`・`filled`・`focused` だけ）
- ラベルは入力欄より前にある。CSS の `+` と `~` は後ろの要素しか選べないので、入力欄からラベルへは進めない
- `<FieldLabel required>` にすると、`<Input required>` と 2 か所に書くことになり、片方を忘れると食い違う

`:has()` なら、`<Input required>` の 1 か所で決まる。

「必須」の文字は TSX に書き、`aria-hidden` を付けた。読み上げソフトには `required` の属性が「必須」と伝えるので、文字まで読むと 2 回になる。入力欄の名前にも混ざらない（`getByRole("textbox", { name: "お名前" })` で確かめた）。

### `outline: none` の注意

`.control` は `outline: none` にして、輪を `.frame` に任せている。`:has()` が使えないブラウザでは輪が出なくなるので、古いブラウザまで支える場合はこの書き方はできない。このリポジトリは新しいブラウザだけを相手にするので、選べた。

## 枠の中の並べ方

**アイコンは重ね、ボタンは並べる**。どちらも枠の中だが、押せるかどうかで変えた。

| 置くもの | 置き方                                    | 理由                                                                                                      |
| -------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| アイコン | `position: absolute` で入力欄の上に重ねる | `pointer-events: none` なら、押すと下の入力欄に当たってフォーカスする。横に並べると、押しても何も起きない |
| ボタン   | `flex` で入力欄の隣に並べる               | 自分で押される。文字がボタンの下に潜らない                                                                |

ボタンには `margin-block: -1px` を付けて、枠の線の上まで広げた。ボタンは `--size-touch-target`（44px）で、枠の内側は線の分だけ小さい（42px）。広げないと、ボタンのある欄だけ 46px になり、隣の欄や `Button` と高さがずれる。

### 入力欄は、余った幅を全部もらう

入力欄（`.control`）には `flex: 1` と `min-width: 0` を付けた。ボタンの分を除いた残りの幅を、入力欄が全部使う。ボタンがなければ、枠の幅を全部使う。`flex: 1` の中身と、`min-width: 0` が要る理由は [docs/04](04-Flexbox%20で並べる.md) の「余った場所を分ける」にある。

```text
枠の幅 400px
┌─────────────────────────────────┬──────┐
│ 入力欄（flex: 1）                │ボタン │
│ 400 − 44 = 356px                 │ 44px │
└─────────────────────────────────┴──────┘
```

## ラベル・説明・エラーの結び付け

`Field` の中に置くと、Base UI が属性を付ける。自分で `id` を考えなくてよい。

| 置いたもの         | `<input>` に付くもの                 | 読み上げソフトの動き         |
| ------------------ | ------------------------------------ | ---------------------------- |
| `FieldLabel`       | `aria-labelledby`                    | 入力欄の名前として読む       |
| `FieldDescription` | `aria-describedby`                   | 名前のあとに読む             |
| `FieldError`       | `aria-describedby`（出ている間だけ） | 説明に続けて読む             |
| 検証で失敗         | `aria-invalid="true"`                | 「無効な入力」のように伝える |

Spring で言えば、`@Valid` が付けた `BindingResult` を、`th:errors` がフィールドの名前で結び付けてくれるのに近い。

並べる順は**ラベル → 説明 → 入力欄 → エラー**にした。Base UI の docs の例は説明が入力欄の下だが、次の理由で上に置く。

- 説明は、打つ前に読むもの
- スマホでは、キーボードや自動入力の候補が、入力欄の下を隠す

間は 4px、項目どうしは 24px（`Form`）にした。`.claude/rules/ux.md` の「ラベルは、対応する入力欄のすぐそばに置く」のとおり、線を引かなくても、余白だけでどのラベルがどの欄のものか分かる。

## いつ検証するか

Base UI の `validationMode` は 3 つ。何も指定しない `onSubmit` のまま使う。

| 値         | 動き                                                   | 向いている場面                               |
| ---------- | ------------------------------------------------------ | -------------------------------------------- |
| `onSubmit` | 送信で検証する。1 回送信したあとは、打つたびに検証する | ふつうのフォーム（初期値）                   |
| `onBlur`   | 欄を離れたときに検証する                               | 使えるユーザー名かどうか、のような確認       |
| `onChange` | 打つたびに検証する                                     | パスワードの強さのような、打ちながら見る情報 |

`onSubmit` の動きを `FixError` のストーリーで確かめた。

```text
"taro" で送信      → エラーが出る。この欄にフォーカスが移り、全部が選ばれる
"taro@" まで打つ   → まだ形が違うので、エラーは残る
"taro@example.com" → その場でエラーが消える
```

打っている最中には責めず、直し終えたら、送信し直さなくても分かる。

最初は「直し始めるとエラーが消える」と思い込んでテストを書き、落ちた。Base UI の `FieldRoot` に `validationMode === 'onSubmit' && submitCountRef.current > 0` のときは変更で検証する処理があり、docs の「afterwards fields will re-validate on change」はこのことだった。

### エラーの文は自分で書く

`<FieldError />` に文を渡さないと、ブラウザの `validationMessage` が出る。ブラウザの言語で決まるので、日本語の画面に英語が出ることがある。なので `match` ごとに文を書く。

| `match`               | いつ                      |
| --------------------- | ------------------------- |
| `valueMissing`        | `required` の欄が空       |
| `typeMismatch`        | `type="email"` の形が違う |
| `tooShort`・`tooLong` | `minLength`・`maxLength`  |
| `patternMismatch`     | `pattern`                 |
| `customError`         | `validate` が文を返した   |

`validate` の失敗は `<FieldError match="customError" />` で、`validate` の返した文がそのまま出る。

サーバーが返したエラーは、`Form` の `errors` に `{ 欄の name: 文 }` で渡し、`<FieldError />`（`match` なし）で出す。打ち直すと消える。

**落とし穴**: `match` なしの `FieldError` は、どの失敗でも出る。`match="valueMissing"` と並べると、空で送信したときに 2 つ出て、片方はブラウザの文になる。今の `ServerError` のストーリーは `required` のない欄なので起きない。`required` の欄にサーバーのエラーを出す場面が来たら考える。

## IME の変換を確定する Enter

Base UI の `Field.Control` は、`<input>` で Enter を押すと検証する（`event.key === "Enter"`）。ところが、IME の変換を確定する Enter でも `key` は `"Enter"` になる。

すると `type="email"` の欄で「やまだ」と打って確定しただけで、「形が違います」が出る。送信のつもりはないのに。

`Input` で、変換中の Enter を Base UI に渡さないようにした。

```tsx
onKeyDown={(event) => {
  if (event.nativeEvent.isComposing || event.keyCode === 229) {
    event.preventBaseUIHandler();
  }
  onKeyDown?.(event);
}}
```

- `preventBaseUIHandler()` は、Base UI の処理だけを止める作法（`handbook/customization.md`）。使う側の `onKeyDown` は呼ぶ
- `keyCode === 229` は Safari のため。Safari は変換が終わってから `keydown` を出すので、`isComposing` が `false` になる。`keyCode` は非推奨だが、これに代わる見分け方がない
- ブラウザの送信（暗黙の送信）は変換中には起きないので、ここまでで足りる。`Textarea` では Base UI が Enter を見ないので要らない

`ImeEnter` のストーリーで確かめた。ガードを外すと、このストーリーは落ちる。

**確かめられていないこと**: ストーリーは `isComposing: true` の `keydown` を送っているだけで、本物の IME は動かしていない。Safari の `keyCode` の分岐も動かしていない。本物の日本語入力で確かめるのは、手元のブラウザで。

AI チャットの「変換中の Enter で送信しない」は、段階 5 で `Textarea` の `onKeyDown` に書く。

## 打った分だけ高くなる Textarea

```css
.textarea {
  min-height: calc(3lh + var(--spacing-8) * 2);
}

@supports (field-sizing: content) {
  .textarea {
    field-sizing: content;
    max-height: calc(10lh + var(--spacing-8) * 2);
    resize: none;
  }
}
```

- **`field-sizing: content`**: 欄の大きさを、中身に合わせる。これまでは JS で `scrollHeight` を測って `height` に入れていた
- **`lh`**: その要素の 1 行の高さ。`3lh` で 3 行分
- **`rows` の代わりに `min-height`**: `field-sizing: content` のときは `rows` が効かない（MDN）
- **`@supports`**: 書いた機能が使えるブラウザにだけ効く。TS の `if ("fieldSizing" in style)` にあたる。Firefox が 152 で対応して、主要なブラウザにそろったのが 2026 年 6 月で、まだ日が浅い。使えないブラウザでは 3 行のまま、`reset.css` の `resize: block` で手で広げられる

Base UI に `Textarea` はない。`render={<textarea />}` で、`Input` の描く要素を替えた。そのため `onChange` などの型は `HTMLInputElement` のままだが、値は `onValueChange` で受けるので困らない。

## 見た目

- **枠線は `--color-input`**: 形を見せる線なので、3:1 以上の色を使う（`--color-border` は飾りの線で薄い）。Switch の溝のために用意してあった
- **文字は 16px**: iOS の Safari は、16px より小さい入力欄にフォーカスすると、画面を拡大する
- **高さは `--size-touch-target`**: Button と横に並べても、高さがそろう
- **エラーは枠の色と文の両方**: 色だけだと、色の見分けにくい人に伝わらない
- **placeholder は例だけ**: 打つと消えるので、ラベルの代わりにしない。Storybook の `Placeholder` にも書いた
- **`.label` は文字の幅だけ**: 横いっぱいにすると、何もない場所を押しても入力欄にフォーカスする

## `/practice` の「カードを足す」

入力欄をページでも確かめるため、カードの一覧の下に、カードを足すフォーム（`features/Card/AddCardForm`）を置いた。見出し（必須・30 文字まで）と本文を入れて「足す」を押すと、一覧の最後にカードが増える。カードと同じく、再読み込みすると元に戻る。

```text
カードを足す
見出し  必須
30 文字まで。一覧のカードの見出しになります。
┌──────────────────────────────┐
│                              │
└──────────────────────────────┘
本文
┌──────────────────────────────┐
│                              │
└──────────────────────────────┘
[足す]
「新しいカード」を足しました。   ← role="status"。読み上げソフトにも伝わる
```

### 足したあとは、Form を作り直して空にする

Base UI の docs には、送信のあとに欄を空にする方法が書かれていない。そこで、Form の `key` を足すたびに変え、React に別の Form として作り直させた。値だけでなく、Base UI が持つ検証の状態（送信した回数など）も最初に戻るので、空になった見出しの欄に「入力してください」が出ない。

TS で言えば、オブジェクトの中身を 1 つずつ消すより、`new` し直すほうが消し忘れがない、という考え方。

作り直すと、押した「足す」ボタンも消えて、フォーカスが `<body>` に落ちる。キーボードの人が今どこにいるか分からなくなるので、見出しの欄にフォーカスを移した。続けてもう 1 枚足すときにも、そのまま打てる。「足しました」の知らせは Form の外に置いて、作り直しても消えないようにした。

### 空白だけの見出しを止める

`required` は、空白だけ（`"   "`）を「入力あり」とみなす。見出しが空のカードができないよう、`Field` の `validate` で止め、`<FieldError match="customError" />` で文を出した。

ここでつまずきかけた。**1 回送信したあとは、`required` で失敗していても `validate` が呼ばれる**（`useFieldValidation.mjs`。打つたびに検証するときは、ブラウザの検証の結果を待たずに `validate` も呼ぶ）。`validate` を「`trim()` して空なら失敗」と書くと、欄を空にしたときに次の 2 つが並んで出る。

- 見出しを入力してください。（`valueMissing`）
- 空白だけの見出しにはできません。文字を入力してください。（`customError`）

空のときは `required` に任せるよう、`validate` は「空ではなく、`trim()` すると空」のときだけ失敗にした。条件を外すと 2 つ並ぶことを、ブラウザで確かめた。

### 確かめた動き

Playwright で `/practice` を開いて確かめた（明るい配色・暗い配色とも同じ）。

| 操作                         | 結果                                                                           |
| ---------------------------- | ------------------------------------------------------------------------------ |
| 空のまま「足す」             | 見出しの欄にフォーカスが移り、「見出しを入力してください。」が出た             |
| 空白を 2 つ打つ              | 「空白だけの見出しにはできません。…」に変わった                                |
| 空白を消す                   | 「見出しを入力してください。」だけに戻った                                     |
| 見出しと本文を入れて「足す」 | 一覧の最後にカードが増え、欄は空でエラーもなく、見出しの欄にフォーカスが移った |
| 見出しの欄で Enter           | 同じように足せた                                                               |

## まだやっていないこと

- **`Fieldset`**: 複数の欄をまとめる部品（住所など）。Checkbox や Radio を作るときに一緒に
- **`Select`・`Checkbox`・`NumberField`**: 実践のお題で要るものから作る。`type="number"` ではなく、Base UI の `NumberField` を使う
- **TanStack Form との組み合わせ**: 項目が多いフォームや、項目どうしの検証（「確認用のパスワードが一致するか」など）が要るときに考える。Base UI の docs（`handbook/forms.md` の TanStack Form）では、Base UI の `Form` は使わず、`form.Field` の中で `Field` に `invalid`・`dirty`・`touched` を、入力欄に `value`・`onValueChange`・`onBlur` を渡す。`ui/` の `Field`・`Input`・`FieldError` はこれらを受け取れるので、作り直さずに使える見込み
- **知らせを Toast に**: 「足しました」と「削除しました」は、今は `role="status"` の段落が別々の場所にある。次の Toast で 1 か所にまとめる
- **ブラウザの自動入力の見た目**: `:-webkit-autofill` の背景は確かめていない
